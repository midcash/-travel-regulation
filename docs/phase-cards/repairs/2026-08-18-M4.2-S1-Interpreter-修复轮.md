# M4.2-S1 Interpreter 修复轮

> 性质：修复卡，不是规格书
>
> 状态：代码与机器验收完成，待人工复核

## 问题

真实 DeepSeek 运行商务差旅请求时，能够提取会议城市、会议地点和会议时间，但不稳定输出通用差旅字段。完整案例缺少 `destination` 与 `date_range`，缺时区案例还缺少 `date_range` 与 `travelers`，导致 Readiness 在 Interpreter 之后正确进入澄清。

## 业务期望

商务会议字段是通用差旅字段的补充，不能替代 `origin`、`destination`、`date_range` 和 `travelers`。用户明确表达的通用事实必须由 Interpreter 提取；事实没有明确表达时必须保持缺失，不由代码推导、默认补全或静默降级。

完整会前到达请求应同时包含通用差旅字段和会议字段，并进入商务范围与初始能力路由。缺少会议时区的请求必须继续澄清，不得推断时区，也不得调用 Planner 或外部研究。

## 当前证据

2026-08-18 的 Live DeepSeek 运行记录显示：BT-ACC-001 的解释类别为 `destination`、会议字段和 `origin`，缺少 `date_range`、`travelers` 与 `meeting_timezone`；BT-ACC-002 的解释类别为会议字段、`origin`、`planning_horizon` 和 `travelers`，缺少 `destination` 与 `date_range`。两次运行均为 Schema 可解析结果，Planner 调用为 0，说明问题位于 Interpreter 语义完整性，不在后续路由判断。

提示修复后的第一次 BT-ACC-002 Live 重跑又暴露了一个同层问题：模型返回的 `extracted_entities[6].value` 不是字符串，`InterpretationResult` 按严格合同拒绝，失败原因为 `LLM_SCHEMA_VALIDATION_FAILED`。这不是放宽 Schema 的理由，而是说明 Prompt 还需要明确嵌套实体字段的 JSON 类型。

## 根因假设

我认为第一层根因是 Interpreter 提示虽然列出了商务会议类别，却没有明确要求会议字段必须与通用差旅字段同时输出，因此模型将会议信息当成了通用差旅信息的替代表达。第二层根因是 Prompt 没有明确约束 `extracted_entities` 的实体值必须是字符串，导致模型偶尔生成 Schema 不接受的对象、数字或数组值。

## 复现

完整案例：

> 我一个人从杭州到上海参加 2026 年 8 月 22 日上午 8 点、中国标准时间的会议，会议地点是上海东方明珠塔，请规划会前到达的差旅方案。

期望同时得到 `origin`、`destination`、`date_range`、`travelers`、`meeting_city`、`meeting_location`、`meeting_starts_at`、`meeting_timezone` 和 `planning_horizon`。

缺失时区案例：

> 我当前在杭州，下周六早上8点我在上海东方明珠塔有一场会议，请规划我的差旅方案。

期望保留已明确的通用字段和会议字段，缺少 `meeting_timezone` 时进入澄清，不推断时区；如果人数没有明确表达，也必须继续保留 `travelers` 阻塞。

## 本轮允许修改

允许修改 Interpreter Prompt 及其版本、Interpreter Prompt 合同测试、人工验收产物中的 Live/离线来源标记和脱敏摘要、对应测试与本修复结果记录。不修改 `InterpretationResult` 结构，不增加目的地或日期的确定性推导，不增加 LLM fallback，不修改 Readiness、ScopeResolver、Router 或 Planner 的业务判断。

## 验收门槛

离线固定响应与真实 LLM 必须分开报告。离线案例验证确定性链路和停止安全性；Live 案例验证真实模型是否同时提取通用字段与会议字段。完整案例缺任一通用硬字段、缺时区案例被错误补全、Planner 在澄清时被调用、或报告不能证明是否真实调用 LLM，均属于阻塞问题。

## 修复结果

Prompt 版本已从 `m2-request-interpreter-v3` 升级为 `m2-request-interpreter-v4`。新规则要求商务字段与通用字段并存，未明确的事实保持缺失，并要求实体值和归一化实体值必须是字符串；没有修改 `InterpretationResult`、Readiness、ScopeResolver 或 Router。

人工验收产物已增加运行来源、真实 LLM 调用标记、网络调用次数和安全失败阶段信息。离线案例明确标记为固定响应且网络调用为 0；Live 案例明确标记为真实 DeepSeek 且网络调用为 1，不保存完整 Prompt 或原始响应。

最终 Live 结果为：BT-ACC-001 正确进入澄清，阻塞项为 `travelers` 与 `meeting_timezone`，没有推断时区，Planner 为 0；BT-ACC-002 正确进入 `meeting_arrival_ready` 初始路由，通用字段和会议字段均存在，能力为 `geo`、`policy`、`intercity_transport`，Planner 为 0，状态为 `collecting`。
