# M1 领域契约与 Schema 快照

## 范围

M1 固化旅行规划后续阶段共同依赖的类型化语言：请求、约束、证据、候选、计划、验证问题、工作流状态、Checkpoint、错误和兼容 Facade。

本文件及 [`data/schemas/m1-domain-contracts.json`](../../data/schemas/m1-domain-contracts.json) 描述当前代码已经实现的契约。它们不表示 M2 及以后能力已经存在。

## 契约分层

| 层 | 契约 | 责任 |
| --- | --- | --- |
| 值对象 | `Money`、`DateRange`、`GeoPoint`、稳定 ID | 金额、日期、坐标和引用 ID 的边界校验 |
| 请求与约束 | `TripRequest`、`Constraint`、`ConstraintSnapshot` | 规划输入、约束来源/硬度和不可变快照 |
| 事实与候选 | `EvidenceItem`、`EvidenceSnapshot`、`Candidate` | 事实引用和可参与规划的标准化选项；M1 只定义结构 |
| 计划与验证 | `ItineraryPlan`、`ValidationIssue` | 版本化计划结构、引用关系和结构化问题；M1 不实现规划算法 |
| 状态与错误 | `TripState`、`Checkpoint`、`WorkflowErrorPayload` | 工作流状态、乐观锁快照载体和安全失败摘要 |
| 兼容边界 | `LegacyPlanResult`、`PlanTripResult` | legacy 自由文本流程只能在 Facade 内部使用，不能越过类型化边界 |

所有 Pydantic 模型都拒绝未知字段（`extra="forbid"`）；领域模型使用不可变配置。跨模块引用使用稳定 ID，不嵌入供应商原始响应。

## 版本与序列化

- 快照顶层 `schema_version` 当前为 `1.0`；各请求模型的 `schema_version` 默认也为 `1.0`。
- 枚举序列化值固定为小写 `snake_case`，例如 `needs_confirmation`、`state_conflict`。
- Decimal、日期和时间遵循 Pydantic JSON Schema/JSON 序列化格式；金额必须带三位大写货币代码。
- 破坏性字段、枚举或语义变更必须提升 Schema 版本，并提供迁移说明；不能静默覆盖旧快照。
- 新增字段必须明确默认值或同步更新所有下游契约测试。删除、改名和放宽校验属于破坏性变更。

## 状态白名单

`TripState.transition_to()` 只允许 `src/domain/models/state.py` 中的显式转换表。状态变更创建新快照并递增 `version`，不原地修改已有对象。状态仓库使用 `expected_version` 做乐观并发控制。

## 兼容 Facade 边界

`PlanTripUseCase.execute()` 接收 `TripRequest`，将其渲染为 legacy planner 的兼容文本，并把 legacy 映射结果包装为 `PlanTripResult`。原始 `dict` 只存在于 Facade 内部的 legacy 边界；CLI 只依赖 Facade 结果。

这仍是 M1 的过渡实现：当前 legacy 结果不是 `ItineraryPlan`，M1 也不调用 LLM 解析 `TripRequest`。后续迁移应先实现类型化解析与规划，再按 M5 计划删除兼容层。

## 快照生成与验证

从仓库根目录运行：

```text
venv/Scripts/python scripts/generate_m1_schema_snapshot.py
venv/Scripts/python -m pytest tests/contract/test_m1_schema_snapshot.py
```

生成器从当前 Pydantic 模型重新生成快照；契约测试会比较完整 JSON 内容。因此模型字段、校验或 discriminated union 发生变化时，测试会要求提交者显式更新快照并审查差异。

快照覆盖领域模型、状态、错误以及 M1 兼容 Facade 的公开模型；它不包含 M2 的意图解析、约束澄清和 Interaction Router，也不代表 M3 的 Evidence Registry 或 Candidate Pool 行为已经实现。
