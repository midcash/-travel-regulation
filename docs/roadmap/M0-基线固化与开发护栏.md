# M0：基线固化、开发护栏与 Eval 起点

## 1. 阶段目标

在不改变用户可见业务能力的前提下，建立可重复、零网络、fail-fast 的开发基线，并创建贯穿后续阶段的版本化评测集。M0 解决“当前行为无法可靠回归、架构收益无法量化”的问题，不开始目标架构功能开发。

## 2. 前置条件

- 当前分支可运行 `venv/Scripts/python main.py`；
- 已检查 `git status` 并识别用户改动；
- 已阅读总路线图、目标架构和 `AGENTS.md`；
- 已记录 Python、依赖、操作系统和当前模型配置。

## 3. 允许修改范围

- `requirements.txt`、`pytest.ini`，可新增 `pyproject.toml`；
- `tests/`、`evaluation/`；
- 最小配置模块和测试辅助设施；
- 与测试隔离、Trace、脱敏有关的最小修复；
- 当前入口的可测试性调整，但不得改变输出语义。

## 4. 禁止事项

- 不创建 M1 领域模型或迁移大目录；
- 不实现 Router、Evidence、Candidate、Task Graph 或 Gate；
- 不更换 LLM/供应商；
- 不加入重试、缓存、fallback 或部分成功；
- 不以“清理”为由删除当前模块；
- 不让默认测试或评测访问真实网络；
- 不用 LLM Judge 替代当前可由代码断言的事实。

## 5. 工作包

### M0-W1：依赖与工具链固化

1. 在当前 venv 解析实际兼容版本；
2. 直接依赖使用精确 `==`；
3. 明确运行时与开发依赖；
4. 配置 `ruff` 和类型检查，检查范围逐步扩大；
5. 注册 `unit`、`contract`、`integration`、`e2e`、`slow` 标记；
6. 默认 pytest 排除 `slow` 且零网络；
7. 建立 CI 最小命令，但 M0 不要求部署。

禁止靠大面积 `# type: ignore` 或降低检查规则制造绿色结果。

### M0-W2：严格模式配置

建立唯一配置入口，至少包含：

```text
strict_mode: bool = true
retry_count: int = 0
cache_reads: bool = false
fallbacks: bool = false
partial_success: bool = false
llm_timeout_seconds
external_api_timeout_seconds
max_revision_rounds
```

规则：

- 开发/测试缺省即 strict；
- 非法布尔值和非法组合启动失败；
- 配置只能由组合根（Composition Root）创建、校验并注入；
- 本地 CLI 的组合根从进程环境变量读取 API Key（`DEEPSEEK_API_KEY`、按功能启用的 `AMAP_API_KEY`/`TUNIU_API_KEY`），不得由领域层、Agent、Gateway 或 Adapter 自行读取环境变量；
- 组合根必须在创建 Planner、Critic、Tool Adapter 和 Orchestrator 之前完成配置校验；缺少当前流程必需的 Key 时，在 Bootstrap 阶段以明确的配置错误 fail-fast，禁止进入 Agent 推理或网络调用；
- 同一个请求生命周期只允许使用组合根创建的同一个不可变 `Settings` 实例；下游组件通过构造函数或 `run(..., settings=...)` 接收配置，不得在执行中重新加载环境；
- `test`/CI 组合根必须显式注入 Fake 配置或测试 Settings，禁止读取开发者真实 `.env`、用户目录或宿主机密钥；
- `production` 组合根只允许从运行时环境变量或密钥系统注入，禁止把密钥写入代码、Fixture、日志或命令行参数；
- `.env` 不是 Python 自动配置源；若本地使用 dotenv，必须由组合根显式加载且仅限 `local` profile，不能改变 `test`/`production` 的来源边界；
- 旧模块读取环境变量仅临时保留并登记迁移任务。

M0-W2 的最小配置装配顺序固定为：

```text
读取进程环境/密钥系统
  → 构造 Settings
  → 校验 strict、超时、预算和必需 API Key
  → 创建 LLM Gateway、Critic、Tool Adapter、Orchestrator
  → 将同一 Settings 注入所有组件
  → 执行请求
```

禁止在 `src/` 业务模块的 import 阶段读取环境变量，禁止用模块级全局 Settings，禁止在缺少 Key 时自动切换 Fake、缓存、估算或备用供应商。

### M0-W3：现有流程特征测试

覆盖：

- `plan()` 初次生成、L1、L2、修订、耗尽和异常；
- `ask_llm` 参数、超时和异常传播；
- JSON 解析的合法、非法和空响应；
- `knowledge.py` 工具入口成功与失败形态；
- CLI 有参数、无参数和内部异常；
- Negation Guard 现有行为。

Offline Suite 中所有 LLM/API 使用显式 Fake；Fake 未配置调用时立即失败。Fake 只用于确定性测试，不是运行时 fallback。M0 同时必须由用户手动执行 Live LLM Smoke，验证真实组合根、API Key、模型、响应非空和基本解析。


M0-W3 必须附带 Live LLM Smoke：

- 标记 `slow` 与 `live_llm`，不进入默认 pytest；
- 使用真实 `DEEPSEEK_API_KEY`，最多 2 次调用、固定超时、`retry_count=0`；
- 至少覆盖一次普通响应和一次当前 Gateway 需要的结构化/可解析响应；
- 断言认证、模型可用、响应非空、解析成功、Token/延迟可记录且 Key 不泄露；
- 任何真实调用失败都阻断 M0，不得改用 Fake、缓存或占位响应继续；
- 将脱敏失败摘要写入 Live 报告，后续可复现失败必须进入 Offline Fixture。
M0 验收必须同时包含 Offline Suite 和 Live LLM Smoke；Fake 通过不能替代真实 API 通过，真实失败也不能改用 Fake 继续验收。

真实 API 验收由用户负责手动执行。Codex 只负责准备命令、测试用例、脱敏报告格式和离线验证，不自动调用真实 API。用户应通过 `start-local.ps1` 或本阶段明确的等价启动方式加载真实配置，并保存模型、调用次数、延迟、Token、失败摘要和报告路径。本次手动真实 API 验收已由用户通过 `powershell -ExecutionPolicy Bypass -File .\start-local.ps1` 执行并确认通过，Live Gate 状态为 `PASSED`，M0 开发阶段结束。

### M0-W4：网络隔离、故障注入与观测基线

- 默认测试安装网络访问 Guard；
- 注入 LLM/HTTP 超时、非法 JSON、空响应、缺少 Key；
- 断言异常不转换为正常方案；
- strict 下每个失败只调用一次；
- 日志不含 Key、完整用户输入和完整行程；
- 为一次 E2E 建立 trace_id、阶段耗时、LLM 调用和 Token 计数。

### M0-W5：版本化求职评测集

在 `evaluation/datasets/` 建立 30～50 条首版用例。M0 只定义评测事实和当前可执行断言，不创建 M1 领域对象。

```text
case_id
dataset_version
user_input
tags
fixture_refs
expected_invariants
forbidden_outcomes
scoring_dimensions
baseline_capability
notes
```

必须覆盖：

- 否定约束、预算边界、日期/天数、人数和特殊人群；
- 需求歧义、关键字段缺失和约束冲突；
- 跨城交通、营业时间、闭馆、行程过密；
- 工具超时、空结果、非法 Schema 和证据冲突；
- 正常规划、需要澄清、应当失败三类终态。

规则：

- 不逐字匹配最终文案；
- 动态事实绑定固定 Fixture；
- 当前无法执行的断言标记 `NOT_SUPPORTED`，不得伪装通过；
- 修改期望结果必须升级版本并记录理由；
- 真实失败案例脱敏后才可加入。

### M0-W6：基线 Runner 与报告

Runner 输出机器可读 JSON 和可审阅 Markdown。报告至少包含：

- 测试数量、覆盖率、数据集版本和标签分布；
- 当前结构化可解析率、硬约束/否定约束可测指标；
- SUCCESS、FAILED、异常吞没、`NOT_SUPPORTED` 数量；
- 平均/P95 延迟、LLM 调用、Token 和可计算 API 成本；
- 当前技术债、未测试真实 API、M1 阻断项。

无法采集的指标标为 `UNAVAILABLE` 并登记补齐阶段，禁止估算。

## 6. 实现顺序

1. 锁定依赖和测试标记；
2. strict 配置；
3. Fake 与网络 Guard；
4. Characterization Tests；
5. Trace/计数最小能力；
6. Dataset Schema 和 5 条冒烟用例；
7. 扩展到 30～50 条；
8. Runner；
9. 基线报告；
10. 独立 Review。

## 7. 测试与评测命令

```bash
venv/Scripts/python -m pytest -m "not slow"
venv/Scripts/python -m pytest tests/unit
venv/Scripts/python -m pytest tests/integration
venv/Scripts/python -m pytest --cov=src --cov-report=term-missing
venv/Scripts/python evaluation/runner.py --dataset baseline-v1 --offline
venv/Scripts/python -m pytest -m "slow and live_llm"
```

最低要求：

- 新增配置和测试辅助模块覆盖率 100%；
- 核心 loop 分支包含通过、修订、耗尽和异常；
- 测试/离线评测真实网络调用数为 0；
- 用户手动执行 Live LLM Smoke 并使用真实 Key 通过，调用次数、Token、延迟和失败分类有报告；
- 未配置 Fake 调用失败；
- 同一 commit 重跑评测结果确定性一致。

## 8. 阶段验收门

- [x] 依赖精确锁定；
- [x] strict 缺省生效；
- [x] 组合根可以从进程环境构造并校验 Settings；
- [x] 缺少当前流程必需 API Key 在 Bootstrap 阶段失败，且未发生 LLM/API 调用；
- [x] Planner、Critic 和后续组件收到同一个 Settings，业务模块不自行读取环境变量；
- [x] 默认测试和离线评测零网络；
- [x] 用户手动执行的 Live LLM Smoke 通过，且失败时未触发 Fake、缓存或降级；
- [x] 当前主流程有特征测试；
- [x] 失败不会被包装为正常成功；
- [x] 日志脱敏测试通过；
- [x] 30～50 条用例通过 Schema 校验；
- [x] 不支持能力明确标记 `NOT_SUPPORTED`；
- [x] 质量、延迟、成本基线报告完成；
- [x] CLI 行为无非预期改变。
