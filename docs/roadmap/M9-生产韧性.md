# M9：生产韧性（可选扩展）

## 1. 阶段定位

M9 不是求职完成条件。只有核心正常/失败路径稳定，并且故障数据证明有收益时，才允许逐项引入可观察、可关闭、可独立测试的韧性机制。

目标不是让所有请求“看起来成功”，而是在不污染政策、航班、酒店、市内交通事实和会议可行性边界的前提下恢复明确的瞬时故障。

## 2. 强制进入条件

- M0～M7 全部验收；若涉及 Action，还必须完成 M8；
- strict E2E 和 Eval 基线稳定；
- Tool/Agent/Gate/State 错误分类完整；
- 指标区分首次成功、恢复成功和失败；
- 故障注入框架可控；
- 真实供应商 SLA、配额和缓存条款已确认；
- 每项机制有独立 Feature Flag、量化目标和回滚方案。

## 3. 永久禁止

- Gate 强制通过；
- 用 LLM 猜测实时价格、库存、班次、路况或公司政策；
- stale Evidence 冒充 verified；
- 隐式部分成功；
- 绕过确认执行 Action；
- Critic/Validator 故障时跳过；
- 恢复成功混入首次成功率；
- strict 模式启用韧性；
- 无限重试、跨越 deadline 或吞掉根因。

## 4. Feature Flags

```text
STRICT_MODE=true
RETRY_ENABLED=false
CIRCUIT_BREAKER_ENABLED=false
CACHE_READS_ENABLED=false
PROVIDER_FAILOVER_ENABLED=false
PARTIAL_RESULT_ENABLED=false
```

strict 优先级最高并关闭所有韧性。每项独立开关，值与 policy version 写入 Trace；非法组合启动失败。

## 5. 子阶段顺序

### M9.1 同源有限重试

只重试连接重置、批准的 5xx、带 Retry-After 的 429。认证、权限、Schema、业务空结果、hard validation、用户取消和非幂等写操作立即失败。

要求：小且固定次数、backoff+jitter、遵守 deadline、每 attempt 独立 Span、保留首次/最终错误、测试断言准确次数。

### M9.2 Circuit Breaker 与限流

- provider + operation 粒度；
- CLOSED/OPEN/HALF_OPEN 可观察；
- 用户错误不计入阈值；
- OPEN 快速失败，不返回假数据；
- HALF_OPEN 有并发上限；
- 状态不跨测试泄露；
- 断路器自身异常 fail closed。

### M9.3 合规缓存

- 只做性能/配额优化，不做错误掩盖；
- key 包含 provider、query fingerprint、policy/document version、locale、currency、date scope、schema version；
- value 保留 Evidence、observed_at、valid_until；
- 动态数据过期后不能 verified；
- cache hit 仍运行 G2/G3；
- 测试默认 cache_reads=false；
- 明确供应商缓存条款。

不实现 stale cache 自动替代关键事实。

### M9.4 备用供应商

第二 Provider 必须通过同一 contract tests。航班、酒店和市内交通分别配置 Provider，不允许跨 capability 隐式替代；选择策略由确定性代码实现，来源变化写入 Evidence，切换后重跑 G2/G3；禁止跨供应商拼接不存在的组合报价。PolicyKnowledgePort 的备用实现必须保持相同文档版本和引用语义，不能用模型常识替代企业政策。

### M9.5 明确标识的非关键部分结果

默认不开启。公司政策、会议要求、去程、已选候选所需的一晚会前住宿、必要市内交通、预算、hard constraint 和 G6 永不允许部分成功。缺失字段显式 `unavailable`，状态与 SUCCESS 不同，不可进入 Action，并向用户展示原因和影响。某住宿候选失败可以淘汰该候选，但不得把不完整候选标成成功；只有与参会可行性无关的解释性或展示性字段才可另行申请 PARTIAL。

## 6. ResiliencePolicy 与状态

```text
ResiliencePolicy
  policy_version
  operation
  retry_policy
  circuit_policy
  cache_policy
  provider_order
  allowed_error_categories
  deadline_budget
  flags
```

结果至少区分：

- `SUCCESS`：首次完整成功；
- `RECOVERED`：触发韧性后完整通过全部 Gate；
- `PARTIAL`：仅批准的非关键缺失；
- `FAILED`；
- `CANCELLED`。

## 7. 指标与评测

- first-attempt success rate；
- recovered rate；
- retry amplification；
- failover rate；
- cache hit/freshness；
- circuit open duration；
- added latency/cost；
- false recovery；
- strict/resilience 质量差异；
- PARTIAL 接受/放弃率。

每个机制先用 M5 数据集和故障集做 strict 对照；没有量化收益或质量下降时停止，不继续下一子阶段。

## 8. 测试策略

每项机制必须覆盖：

1. flag off 与 M7/M8 原行为一致；
2. strict on 强制不触发；
3. allowed failure 恢复；
4. disallowed failure 立即失败；
5. deadline/budget 耗尽；
6. 指标、Trace 和错误链；
7. 并发与状态隔离；
8. 非法配置；
9. 回滚开关；
10. 故障注入 E2E；
11. 政策、去程、已选候选所需的一晚会前住宿和 local transport 的关键性分类不可被配置降级。

故障集覆盖 timeout、5xx、429、认证、Schema 漂移、空/慢响应、半开探测、缓存污染、主备同时失败。

## 9. 灰度顺序

1. 本地 strict + 专项测试；
2. 预发布故障注入；
3. shadow 记录、不执行；
4. 小比例只读流量；
5. 对照首次成功与恢复质量；
6. 超过错误/延迟/成本阈值自动关 Flag；
7. 人工评审后扩大；
8. 记录 ADR 和回滚结果。

Action 写操作不得作为首批灰度对象。

## 10. 阶段验收门

- [ ] strict 行为完全不变；
- [ ] 每项机制独立关闭；
- [ ] 恢复后仍全量通过相关 Gate；
- [ ] 来源、attempt 和 policy version 可追溯；
- [ ] 无估算替代、强制通过、隐式部分成功；
- [ ] 参会关键组件在任何 Feature Flag 组合下都不能返回 PARTIAL success；
- [ ] SUCCESS/RECOVERED/PARTIAL/FAILED 指标分离；
- [ ] 故障注入和回滚演练通过；
- [ ] 量化收益大于延迟、成本和复杂度。

## 11. 交付清单

- ResiliencePolicy 与 Flags；
- 经批准的 retry/circuit/cache/failover；
- 可选且单独批准的 PARTIAL；
- 指标、Trace、告警；
- 故障注入测试；
- 灰度/回滚手册；
- 每个子阶段独立 ADR 和量化报告。
