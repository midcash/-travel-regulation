# EVAL-OBS-1 评测基线可视化与观测面提案的设计说明

> 文档性质：面向项目维护者的设计解释与取舍说明  
> 对应提案：`EVAL-OBS-1-评测基线可视化与观测面提案.md`  
> 阶段关系：M4.1 已完成验收；本说明不属于 M4.1 完成条件，也不改变 M4.2 的前置状态  
> 文档目的：帮助首次接触项目的人理解“为何这样观测、观测什么、凭什么验收”，而不是替代机器可执行的 Spec。

## 摘要

M4.1 已验收的评测基线能够保存日志、评分结果和最终状态，但不足以回答评测链路中的因果问题：某个案例如何进入不同评测路线，某一节点实际接收了什么、产生了什么，指标依据哪一份 Oracle 计算，以及最终失败究竟源于业务断言、外部依赖还是评测器自身。若直接在现有日志之上构建 Dashboard，界面只能进行文本聚合，无法形成可重放、可审计、可解释的证据链。因此，本提案将可观测性定义为独立于 UI 的评测数据合同：由受控运行输入 `RunSpec`，由节点级 `EvaluationEvent` 记录过程，由 `FailurePacket` 固化失败因果，由不可变 Artifact 保存结果，再由 Dashboard 读取和解释。

该设计的核心结论是：Dashboard 不负责评测，事件不负责改变评测，观测层只负责把既有 Runner、Scorer 和验收器的真实行为转化为可回放证据。这样可以在不修改 M4.1 Oracle、评分公式和业务语义的前提下，解决“只有日志和最终 pass”造成的不可解释性；它仍然是 M4.1 之后的独立增量，不会重新打开 M4.1 验收。

## 一、问题定义与系统边界

M4.1 的目标是建立商务差旅改造前的可重复基线，而不是证明当前系统已经完成差旅语义能力。其有效性取决于两点：一是评测器能够对冻结数据集和 Oracle 做确定性判断；二是评测结果能够说明当前实现首先在哪一层失效。可观测性补充因此不把“展示更丰富”作为唯一目标，而把评测过程重构为一条具有身份、顺序、来源、产出和失败归属的证据链。

本提案与原 M4.1 的关系是正交的。原 Spec 决定测试什么、如何评分以及何时验收；本提案只决定如何把这些事实记录为可追溯事件。二者之间不允许出现第二套 Oracle、第二个 Scorer 或由前端推导出的验收结论。界面可以解释 `business_assertion=FAIL` 的原因，但不能将其改写为成功；也不能因为某个节点没有日志而推定其通过。

## 二、输入冻结与输出分层

可观测评测从冻结 `RunSpec` 开始。数据集版本与哈希、案例顺序、Oracle 版本、Fixture、Policy、代码提交、模型配置、执行模式和调用预算都必须在运行前确定，并在运行中保持不变。该约束解决的是评测可比性问题：如果一次运行悄然换了数据集、模型或策略，后续的指标差异就不能归因于代码变化，M4-before 也失去基准意义。

案例输入仍由现有 `AgentEvalCase` 合同校验，观测层只增加来源与安全摘要。节点之间继续传递类型化合同或 Artifact 引用，而不是借助自由文本进行跨模块判断。这样既保持项目“结构化契约优先”的总架构，又使观测层能够回答输入来自何处、使用了哪一版规则、是否经过校验。

输出采用分层状态模型。`evaluation_status` 表示评测器和验收流程是否有效完成，`business_assertion` 表示案例是否满足 Oracle，`run_status` 表示运行本身是否完整，`live_status` 表示真实模型路线是否执行成功。四者分离是验收成立的必要条件，因为“评测器运行成功但业务断言失败”正是 M4.1 基线最有价值的结果之一。若将这些状态合并成一个 PASS，评测器的正确性、业务实现的成熟度和外部依赖的可用性便会被错误地混为一谈。

## 三、阶段事件为何是最小充分观测单位

可观测性采用节点级事件而非 Token 级流式输出。一个节点事件至少包含运行、路线、案例、节点、版本、序号、事件类型、状态、输入输出引用、期望引用、指标引用、失败包引用、调用计数和四类指纹。该集合覆盖了执行过程的四个基本问题：何时执行、执行什么、得到什么、依据什么判定。Token 级输出既不能替代这些结构化字段，又会扩大隐私泄露和事件噪声，因此不属于 M4.1 的必要观测粒度。

事件类型按照评测生命周期排列：运行创建、资产校验、路线开始、节点开始、节点输出、指标计算、节点失败或阻断、路线完成、Artifact 写入、验收完成和运行结束。顺序以单调 `sequence` 为准，而不是以时间戳为准；事件先追加到持久化存储，再向前端推送。由此，前端断线只会暂时失去实时展示，不会破坏评测本身，也能够使用 `run_id + after_sequence` 从历史位置恢复。

这一设计还解决了“阶段没有输出”这一常见歧义：没有事件只能表示未运行、被上游阻断或评测器异常，不能自动解释为成功。上游失败后下游必须显式产生 `BLOCKED_BY_UPSTREAM` 或 `NOT_RUN`，从而避免空结果被误计为零错误或部分成功。

## 四、Failure Packet 的因果解释作用

传统日志通常描述“发生了异常”，但不保证能确定第一个违反合同的节点。Failure Packet 将失败固定为结构化对象，关联 `failure_id`、首个失败节点、首个失败阶段、失败类别、稳定错误码、脱敏根因摘要、期望与实际引用、受影响指标、上游事件、下游状态、追踪身份和 Artifact。其目的不是保存更多异常文本，而是使失败能够被分类、聚合、回放和验收。

首因规则要求最早违反输入合同或 Oracle 的节点拥有失败归属，后续传播只产生阻断事件，不得覆盖首因。案例期望与实际不一致属于 `BUSINESS_FAILURE`；外部 LLM、网络、超时或限流属于 `EXTERNAL_DEPENDENCY_FAILURE`；数据集、Schema、Scorer 或观测合同不可用属于 `EVALUATOR_ERROR` 或 `CONFIGURATION_ERROR`。这一分类使 Dashboard 能够分别回答“业务需要修复什么”“环境是否可用”“评测器是否可信”，而不是只输出一个失败总数。

Failure Packet 还承担安全边界。完整堆栈、Prompt、用户原文和供应商响应不能被当作默认诊断信息推送；需要深度调试时，只能将受控本地 Artifact 作为引用对象，并以哈希与权限控制进行关联。这样既保留审计能力，也避免观测面成为新的敏感数据出口。

## 五、脱敏边界的必要性

评测输入往往包含自然语言请求、行程信息和外部供应商响应，真实 Live 路线还涉及模型配置和凭证。若只在 UI 层隐藏敏感字段，原始日志、JSONL、报告或 API 仍可能泄露，因此 Spec 把脱敏置于事件写入边界之前。凭证、Authorization、Cookie、完整 Prompt、系统指令、姓名、联系方式、证件、完整行程、支付信息、供应商原始响应以及 URL 查询参数中的秘密均不得进入普通观测产物。

允许保留的是完成评测解释所必需的最小信息，包括稳定身份、长度、数量、枚举、不可逆哈希、Schema 版本、Artifact 相对引用、时间、耗时、指标值、调用计数和指纹。城市、日期等业务字段只有在已经脱敏且确实支撑 Oracle 解释时才能保留。该取舍牺牲部分即时调试便利，换取评测系统在离线报告、实时推送和后续扩展中的安全可控性。

## 六、可插拔设计与后续扩展

M4.1 当前节点具有明显的阶段性，后续 M4.2、M4.3 可能增加 Scope Resolver、Policy Retrieval、Evidence Registry、Candidate Pool、Planner 或 Validator。如果 Dashboard 依赖固定页面字段和固定流程分支，每次模块升级都会产生高耦合修改。补充 Spec 因而将节点元数据抽象为注册表：节点以稳定 ID、版本、输入输出 Schema、拥有指标、失败类别、上下游关系和原理引用注册；观测层只消费统一事件，不直接依赖节点内部实现。

可插拔的验收标准不是“新增节点后页面仍能打开”，而是“注册测试节点且不修改 Dashboard 聚合逻辑时，该节点能够自动出现在路线、节点、失败和原理视图中”。这项约束把 Dashboard 从 M4.1 专用页面提升为评测观测面，同时仍将业务逻辑留在 Runner 和节点 Adapter 内部，避免观测层反向控制系统。

## 七、为何这些验收条件能够成立

本补充采用合同、链路、结果一致性、失败、安全、幂等回放和可插拔七类验收。合同验收证明事件与失败包本身可被机器解析；链路验收证明所有 M4.1 路线都有事件覆盖；结果一致性验收证明观测层没有创造第二套评分；失败验收证明首因和下游阻断没有被空结果掩盖；安全验收证明敏感内容不会从任一观测出口泄露；幂等与回放验收证明实时展示不是一次性、不可恢复的过程；可插拔验收证明后续扩展不需要重写 Dashboard 核心。

这些条件之所以足以支撑验收，是因为它们分别覆盖了评测系统的四种可信性：输入可信，即知道评测使用了什么；过程可信，即知道每一步是否真正执行；结论可信，即知道指标和最终状态如何由事件与 Oracle 推导；运行可信，即失败、重试、断线、重复消费和敏感数据处理均有明确边界。它们不要求当前业务案例已经通过，反而要求业务失败能够被稳定、正确和可解释地保留下来。

## 八、重要取舍与实施边界

第一，选择“先持久化、后推送”，牺牲极低的展示延迟，换取事件不因浏览器断线而丢失；第二，选择节点级而非 Token 级观测，牺牲模型生成过程的细粒度，换取隐私、安全和可读性；第三，首版允许 JSONL 或 SQLite 作为存储适配器，暂不绑定 FastAPI、SSE 或 WebSocket，避免 UI 技术反向冻结评测合同；第四，按钮只启动预定义的 `offline` 或 `all` 任务，不接受任意命令，牺牲自由度以保护运行边界和结果可复现性。

本文件不宣称 Dashboard、API、事件存储适配器已经实现，也不允许通过增加观测字段来修改 M4.1 业务行为。正确的实施顺序应是先建立事件、Failure Packet、脱敏和追加存储合同，再接入 Offline/Live Runner，最后实现运行入口和界面。若顺序倒置，系统可能得到一个视觉上完整、但无法证明其数据来源和验收正确性的控制台。

## 结论

M4.1 可观测性补充的本质不是增加图表，而是建立从冻结输入到最终状态的评测证据链。`RunSpec` 保证可比，`EvaluationEvent` 保证过程可见，`FailurePacket` 保证失败可归因，脱敏边界保证观测可安全扩展，Node Registry 保证链路可插拔，回放与一致性验收保证 Dashboard 不会取代真实评测。只要后续实现严格遵守这组合同，初次接触项目的人即可沿着数据集、Oracle、路线、节点输出、评分依据、失败首因和 Artifact 逐层理解 M4.1 做了什么；维护者也能够判断哪些结果是业务改进，哪些只是评测器或环境变化。
