# M1：结构化契约与状态

## 1. 阶段目标

建立所有后续阶段依赖的类型化语言：请求、约束、证据、候选、计划、验证问题、错误和工作流状态；提供可测试的 InMemory 状态仓库，并通过兼容 Facade 保持现有 CLI 可用。

## 2. 前置条件

- M0 全部验收通过；
- 默认测试零网络；
- strict 配置已集中管理；
- 当前自由文本流程有稳定特征测试；
- M0 Live LLM Smoke 已通过，真实 API 配置可用。

## 3. 允许修改范围

- 新增 `src/domain/models/`、`src/domain/errors.py`；
- 新增 `src/ports/state_repository.py`、`src/ports/clock.py`；
- 新增 `src/infrastructure/persistence/in_memory.py`；
- 新增 Mapper、Facade 和对应测试；
- 对 `main.py`、`engine/loop.py` 做兼容接入；
- requirements 中加入精确锁定的 Pydantic v2。

## 4. 禁止事项

- 不调用 LLM 解析 `TripRequest`；
- 不实现 Interaction Router；
- 不接真实工具；
- 不实现 Evidence Registry 行为、Candidate 排序或 Task Graph；
- 不改变当前方案生成逻辑；
- 不创建无字段约束的“万能 BaseModel”；
- 不允许 `extra="allow"` 吞掉未知字段；
- 不使用可变默认值；
- 不用 `dict[str, Any]` 逃避建模。

## 5. 目标模型

### 5.1 通用枚举和值对象

至少定义：

- `InteractionMode`：ANSWER、CLARIFY、PLAN、REFINE、COMPARE、REPLAN、ACTION、UNSUPPORTED；
- `ConstraintHardness`：HARD、SOFT、ASSUMPTION、UNKNOWN；
- `EvidenceStatus`：VERIFIED、CONFLICTING、STALE、UNAVAILABLE；
- `WorkflowStatus`：COLLECTING、CLARIFYING、RESEARCHING、DRAFTING、VALIDATING、REPAIRING、NEEDS_CONFIRMATION、CONFIRMED、STALE、REPLANNING、COMPLETED、FAILED；
- `IssueSeverity`：INFO、WARNING、BLOCKING；
- `ErrorCategory`：VALIDATION、CONFIGURATION、LLM、TOOL、EVIDENCE、BUDGET、TIMEOUT、STATE_CONFLICT、SECURITY、INTERNAL；
- `Money`、`DateRange`、`GeoPoint`、稳定 ID 类型。

所有枚举序列化值固定为小写 snake_case；发布后更改需版本迁移。

### 5.2 TripRequest

字段至少包含：

- `request_id`、`trip_id`、`session_id`；
- origin、destinations；
- date window 或明确 duration；
- travelers（成人、儿童、老人、无障碍需求）；
- budget（金额、币种、范围/上限语义）；
- preferences、explicit exclusions；
- locale、timezone；
- requested mode、raw input reference；
- schema version。

校验：日期关系、人数、货币、预算正值、目的地非空；未知字段拒绝。

### 5.3 Constraint 与 Snapshot

`Constraint` 必须包含：id、category、normalized value、hardness、priority、scope、source、confidence、user_confirmed、conflict_group。

`ConstraintSnapshot`：

- 不可变；
- 包含 version、created_at、request_id；
- hard/soft/assumption/unknown 可查询但内部只有一个事实来源；
- 创建后不能原地修改，只能产生新版本；
- hard constraint 冲突必须显式表示，不能按最后写入覆盖。

### 5.4 Evidence、Candidate、Plan

M1 只定义契约，不实现 M3 行为：

- `EvidenceItem` 含 source、source_ref、observed_at、valid_until、status；
- `Candidate` 使用 discriminated union 表示 transport/stay/place/context；
- `ItineraryPlan` 含 plan_id、version、status、days、items、alternatives、budget、buffers、assumptions、warnings、evidence_refs；
- 所有引用必须使用 ID，不嵌入完整原始响应。

### 5.5 ValidationIssue 与 WorkflowError

`ValidationIssue`：gate、severity、type、affected_ids、constraint_refs、evidence_refs、message、repair_strategy、retryable。

`WorkflowError`：

- `trace_id`、stage、category、code、safe_message；
- upstream refs；
- retryable；
- cause 只留内部，不序列化给用户；
- 不得包含 API Key 或完整 PII。

## 6. 状态仓库

定义 `StateRepository` Port：

```python
class StateRepository(Protocol):
    def create(self, state: TripState) -> TripState: ...
    def get(self, trip_id: TripId) -> TripState: ...
    def save(self, state: TripState, expected_version: int) -> TripState: ...
    def checkpoint(self, trip_id: TripId) -> Checkpoint: ...
    def list_checkpoints(self, trip_id: TripId) -> tuple[Checkpoint, ...]: ...
```

InMemory 实现要求：

- 深拷贝或不可变模型，调用者不能旁路修改；
- 乐观并发控制，版本不一致抛 `StateConflictError`；
- Checkpoint 保留策略可配置，默认测试至少 3 个；
- 不使用全局单例；
- 测试之间完全隔离；
- 不做磁盘 IO。

## 7. 兼容 Facade

创建稳定 Use Case/Fascade，例如：

```python
class PlanTripUseCase:
    def execute(self, request: TripRequest) -> PlanTripResult: ...
```

M1 内部仍可调用 legacy `engine.loop.plan()`，但必须：

- 由 Mapper 将结果转换为类型化结果；
- legacy 原始 `dict` 不得越过 Facade；
- 兼容层标记在 M5 删除；
- 新代码禁止直接调用 `engine.loop.plan()`；
- CLI 输出保持兼容。

## 8. 实现顺序

1. 值对象、枚举与错误；
2. TripRequest/Constraint；
3. Evidence/Candidate/Plan/Validation 契约；
4. TripState 与状态转换白名单；
5. StateRepository Port + InMemory；
6. legacy Mapper；
7. PlanTripUseCase Facade；
8. CLI 组合根切换到 Facade；
9. 契约文档与 JSON Schema 快照。

## 9. 测试矩阵

- 每个模型：最小合法、完整合法、缺字段、未知字段、边界值、非法组合、序列化往返；
- Snapshot：不可变、版本递增、冲突保留；
- State：每条允许/禁止转换；
- Repository：create/get/save、并发冲突、Checkpoint、隔离；
- Error：安全序列化、cause 不泄露；
- Mapper：legacy 正常、缺字段、异常结果；
- Facade：旧 CLI 回归；
- Property-based 测试可用于 Money、日期和状态转换，但不是必选依赖。

覆盖率：新增 domain、ports、InMemory 和 Mapper ≥ 95%。


### 9.1 Live 回归门

M1 不实现 LLM 解析，但阶段升级仍必须由用户手动重跑 `live_llm` Smoke，确认 Facade、配置装配和 Gateway 兼容性未退化。该门最多 2 次真实调用，失败即阻断 M1；不得用 Fake 结果替代真实回归。
其余契约、状态和 InMemory 测试使用显式 Fake/Fixture，默认 CI 零网络；Live Smoke 与离线测试都是阶段证据。

真实 API 验收由用户负责手动执行。Codex 不自动调用真实 API，只准备命令、测试和脱敏报告格式。用户应通过 `start-local.ps1` 或本阶段明确的等价启动方式加载真实配置并保存验收证据；未提供证据时，Live 回归门状态为 `PENDING_MANUAL_ACCEPTANCE`，不得标记 M1 完成。
