# ADR-M1：结构化契约与状态边界

- 状态：Accepted
- 日期：2026-07-29
- 阶段：M1

## 背景

M0 的主链路仍以自由文本规划为中心。M2～M6 需要共同依赖稳定的请求、约束、证据、候选、计划、验证问题、状态和错误类型；如果继续跨模块传递裸 `dict`，后续解析、路由、研究和验证会缺少可检查的边界。

## 决策

### 1. 领域模型边界

M1 使用 Pydantic v2 固化以下契约：

- `TripRequest`、`Constraint`、`ConstraintSnapshot`；
- `EvidenceItem`、`EvidenceSnapshot`、`Candidate`、`ItineraryPlan`；
- `ValidationIssue`、`TripState`、`Checkpoint`、`WorkflowError`；
- `Money`、`DateRange`、`GeoPoint` 及稳定 ID 值对象。

所有核心模型使用 `extra="forbid"`；不可变快照和状态版本通过 `frozen` 模型与新版本对象表达。动态事实只通过稳定 `evidence_id` 引用，领域模型不嵌入供应商原始响应。

### 2. Schema 与版本策略

当前公开契约 Schema 版本冻结为 `1.0`，枚举值使用小写 `snake_case`。契约快照位于 [`data/schemas/m1-domain-contracts.json`](../../data/schemas/m1-domain-contracts.json)，由 [`scripts/generate_m1_schema_snapshot.py`](../../scripts/generate_m1_schema_snapshot.py) 从当前模型生成，并由契约测试校验。

破坏性字段、枚举或语义变更必须提升 Schema 版本，同时提供迁移说明；禁止静默覆盖旧快照。新增字段必须同步更新下游契约测试。

### 3. 状态存储边界

通过 `StateRepository` Port 隔离状态存储。M1 提供无磁盘 I/O 的 `InMemoryStateRepository`，使用深拷贝/不可变模型保护调用方，使用 `expected_version` 实现乐观并发控制，并保留可配置数量的 `Checkpoint`。

后续持久化实现只能替换 Port 的实现，不改变领域模型或用例接口。

### 4. Legacy 兼容与删除计划

`PlanTripUseCase` 是当前 CLI 的唯一兼容入口。它接收 `TripRequest`，在 Facade 内渲染 legacy 文本，并通过 `LegacyPlanMapper` 将旧结果校验为 `LegacyPlanResult` 后再暴露 `PlanTripResult`。新代码不得直接调用 `engine.loop.plan()`，原始映射只允许存在于 Facade 内部。

M1 保留 `src/engine/loop.py`，因为 M1 尚未实现自然语言到结构化请求的解析，也不实现结构化行程规划。M2～M5 逐步迁移消费者并增加契约回归；待调用者归零、回归覆盖完成且 M5 验收通过后删除兼容层。M1 不提前删除 legacy，也不把 legacy 字符串伪装成 `ItineraryPlan`。

## 未决事项与范围边界

以下能力明确留给后续阶段：

- M2：LLM 约束解析、澄清和 Interaction Router；
- M3：真实工具 Adapter、Evidence Registry 行为和 Candidate Pool；
- M4：Task Graph、Research Agent 和混合规划；
- M5：质量门、独立 Critic 和局部修复；
- SQLite、缓存、重试、备用供应商、部分成功和外部写操作。

## 结果

M1 为后续阶段提供可序列化、可测试、可演进的类型边界，同时保持现有 CLI 的兼容行为。M1 的限制和迁移责任记录在 [`evaluation/reports/M1-handoff.md`](../../evaluation/reports/M1-handoff.md)。
