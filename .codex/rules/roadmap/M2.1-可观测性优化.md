# M2.1：M2 主链路可观测性优化

阶段定位：M2 验收后的非功能性加固。只提升请求关联、阶段产出可见性、失败诊断和 legacy Critic 修订可解释性，不改变 M2 业务行为，不提前实现 M3～M9 能力。

## 1. 阶段目标

让一次本地或测试请求能够仅凭脱敏日志和 Trace 回答：

1. 请求经过了哪些阶段，每个阶段是否成功、耗时多久；
2. 每一步产生了什么类型化结果摘要；
3. Router 为什么选择当前模式，澄清由哪些 blocker 触发；
4. 工作流失败在哪一阶段，错误代码、安全摘要、上游引用和可重试性是什么；
5. legacy Critic/L1 为什么要求 Planner 修订，本轮修订针对哪些问题；
6. 同一请求的 CLI 输出、结构化日志、LLM Span 和失败事件如何关联。

M2.1 不以增加日志数量为完成标准，而以“能够从一个 `trace_id` 定位阶段、产出、决策和失败原因”为完成标准。

## 2. 前置条件

- M2 已验收，`RouteDecision`、`ConstraintSnapshot`、`ReadinessResult` 和 `WorkflowErrorPayload` 契约可用；
- M2 Offline Suite 与 Live LLM Gate 的既有报告可作为行为基线；
- `structlog`、OpenTelemetry 和 `prometheus_client` 已存在，不为 M2.1 引入新的观测框架；
- strict 模式、`retry_count=0`、无 cache/fallback/partial success 持续有效；
- 开工前保存同一组 M2 输入的路由结果、错误载荷、LLM 调用次数和日志样本。

## 3. 不影响 M3 及后续阶段的硬边界

### 3.1 契约冻结

M2.1 禁止修改以下业务语义：

- `TripRequest`、`ConstraintSnapshot`、`ReadinessResult`、`RouteDecision` 的字段、枚举和决策优先级；
- G0 规则、RequestInterpreter Prompt/Schema、ConstraintService 归一化规则；
- ClarificationBuilder 的问题选择、排序和数量；
- TripState 合法状态转换；
- Planner、L1、L2 的判断结果、修订轮次和调用预算；
- M3 的 Provider、ToolError、Evidence、TTL、Candidate 契约。

允许使用 `TripState.last_error` 和 `WorkflowError.public_payload()` 等已有字段记录既有失败，不得为观测需要新增业务分支。

### 3.2 行为隔离

- 观测代码只能读取既有输入/输出并生成脱敏摘要，不得参与路由、约束、评分、Gate 或修订判断；
- 开启或关闭观测后，业务返回值、异常类型、状态转换、Prompt、LLM/工具调用次数必须一致；
- 观测发送失败不得被伪装成业务成功，也不得把原本成功的业务请求改成失败；本地 strict 环境必须产生独立的 `observability_emit_failed` 安全告警；
- 不增加任何 LLM 或外部 API 调用；
- 不在 `src/domain/` 中引入 logger、OpenTelemetry 或 Metrics 依赖，埋点放在 presentation、application 边界或 observability infrastructure；
- M3 及后续阶段可以复用事件封装和 Trace helper，但其业务代码不得依赖观测事件才能运行。

### 3.3 明确不做

- 不实现 M3 Tool Adapter、Evidence Registry、Candidate Pool；
- 不实现 M4 Task Graph、Research Agent 或混合规划；
- 不把 legacy L2 升级为 M5 `CriticAgent`，不实现 `ValidationIssue` 驱动的 Repair；
- 不实现 M6 API、Demo 或远端可观测平台；
- 不实现 M7 计划版本与 Replan；
- 不增加 retry、cache、fallback、估算、部分成功或 Gate 强制通过；
- 不记录完整用户输入、Prompt、LLM 响应、完整行程、联系方式、证件或凭证。

## 4. 目标观测模型

### 4.1 请求关联

每次请求建立一个根观测上下文，至少携带：

```text
trace_id
otel_trace_id
request_id
trip_id
session_id
workflow_status
state_version
```

约束：

- `trace_id` 继续使用应用层稳定业务关联 ID；
- `otel_trace_id` 使用 OpenTelemetry 标准 Trace ID；
- 根 Span 把业务 `trace_id` 写入 `workflow.trace_id` 属性；
- 同一请求的所有结构化日志同时携带二者，禁止再产生无法与业务请求关联的孤立 LLM Span；
- Metrics label 禁止使用 `trace_id`、`request_id`、`trip_id`、`session_id` 等高基数字段。

### 4.2 统一事件外壳

事件至少包含：

```text
event
level
timestamp
trace_id
otel_trace_id
stage
status
duration_ms
```

按事件类型补充低敏字段：

```text
request_id / trip_id / session_id
state_before / state_after / state_version
category / code / retryable / cause_type
input_count / output_count / schema_version
reason_codes / blocker_codes / issue_refs
model / token_count / finish_reason
```

禁止把任意 Pydantic Model 直接 `model_dump()` 后写入日志。每个阶段必须使用显式字段白名单构造摘要。

### 4.3 阶段与安全产出摘要

| 阶段 | 完成事件应记录 | 禁止记录 |
|:---|:---|:---|
| Request | 输入字符数、请求身份、初始状态版本 | 原始输入 |
| G0 | passed、issue codes、safety flags、PII 布尔值 | 命中原文、脱敏前 PII |
| Interpreter | Prompt/Schema 版本、mode hint、候选类别、数量、置信度 | Prompt、模型原始响应、实体原文 |
| ConstraintService | Snapshot 版本、约束数量、类别、冲突组数量 | 完整约束值和原始用户文本 |
| ReadinessEvaluator | ready、blocker codes/IDs、assumption codes、置信度 | 用户敏感字段值 |
| Router | mode、reason codes、required capabilities、missing blocker IDs | 自由文本推理链 |
| State | 状态前后、版本前后、失败载荷引用 | 完整 TripState |
| LLM | model、tokens、耗时、finish reason、failure type | Key、Prompt、response |
| legacy Planner | round、plan chars、耗时 | 完整计划 |
| L1/L2 Critic | pass、来源、issue count、issue refs、安全摘要引用 | 完整评审响应 |
| Revision | round、trigger、issue refs、修订前后长度或摘要 hash | 完整修订 Prompt、完整计划 |

## 5. Trace 层级

M2.1 的本地请求 Trace 至少为：

```text
workflow.request
  ├── stage.g0
  ├── agent.request_interpreter
  │   └── gen_ai.chat
  ├── stage.constraint_snapshot
  ├── stage.readiness
  ├── stage.route
  ├── stage.state_persistence
  └── legacy.plan（仅 PLAN）
      ├── agent.planner
      │   └── gen_ai.chat
      ├── gate.l1
      ├── agent.legacy_critic
      │   └── gen_ai.chat
      └── legacy.revision（按实际轮次）
          └── gen_ai.chat
```

Span 规则：

- 父子关系必须由当前 context 自动传播，不手工伪造 parent ID；
- Span 名称和属性使用稳定低基数值；
- 失败 Span 设置 error status，并记录安全 `error.type`、`workflow.stage`、`workflow.code`；
- 不使用 `"default"` 代替真实 session/request 关联；
- Console Span 与应用 JSON 日志必须能分离输出，避免终端混杂后无法阅读。

## 6. 错误诊断规范

捕获 `WorkflowError` 时必须记录其安全载荷：

```text
trace_id
stage
category
code
safe_message
upstream_refs
retryable
cause_type
```

规则：

- `safe_message` 来自 `WorkflowErrorPayload`，不得直接记录任意异常字符串；
- `cause_type` 只记录异常类名；需要堆栈时进入受控开发日志，并经过凭证/PII 脱敏；
- 非 `WorkflowError` 统一分类为 `UNEXPECTED_INTERNAL_ERROR`，记录阶段、异常类名和关联 ID，不向用户暴露内部异常文本；
- Facade 进入 `FAILED` 时，把已有 `WorkflowErrorPayload` 写入现有 `TripState.last_error`；
- 失败状态持久化自身失败时，保留原始错误为主错误，并增加独立的 state persistence failure 事件，禁止覆盖根因；
- CLI 至少展示可安全复制的 `trace_id + stage + code + safe_message`。

## 7. legacy Critic 与修订原因

M2.1 只为当前 legacy 规划链增加审计信息，不改变 L1/L2 返回值和修订算法。

每轮必须形成以下事件：

```text
legacy_review_completed
  round
  l1_passed
  l1_issue_count
  l2_passed
  l2_issue_count
  issue_refs

legacy_revision_requested
  round
  trigger_sources
  issue_refs
  issue_summary_ref

legacy_revision_completed
  round
  duration_ms
  output_chars
```

其中：

- `issue_ref` 是本次运行内稳定、不可反推原文的引用；
- 日志可记录经过白名单和长度限制的安全问题摘要；无法证明安全时只记录 `issue_summary_ref`；
- L1 与 L2 原因必须分开计数，禁止统一写成 `reason=l2_review`；
- 修订耗尽时记录仍未解决的 issue refs 和轮次，不得把耗尽视为成功；
- 本步骤不把自由文本问题升级为领域 `ValidationIssue`，该迁移仍由 M5 负责。

## 8. 输出与存储分层

本地运行输出分为：

1. **CLI 用户输出**：路由、澄清、计划或安全错误摘要；
2. **应用 JSONL 日志**：阶段事件、决策、错误和低敏产出摘要；
3. **OpenTelemetry Trace**：父子 Span、耗时、状态和关联属性；
4. **Metrics**：聚合成功率、失败分类、延迟、调用和修订轮次。

要求：

- stdout/stderr 的职责固定并有测试；
- 默认本地输出不得同时把完整 Console Span JSON 插入人类可读结果中；
- 若写入本地文件，路径、轮转和 Git ignore 必须明确，运行产物不得提交；
- M2.1 不部署 Phoenix、Langfuse、Jaeger、Prometheus Server 或其他远端平台；M6 再实现展示和部署。

## 9. Metrics

M2.1 只增加低基数指标：

- workflow 请求成功/失败数；
- 各 stage 成功/失败数和耗时；
- route mode 数量；
- clarification blocker 数量和 blocker code 分布；
- interpreter Schema/解析失败数；
- LLM 调用、Token、耗时和 finish reason；
- legacy L1/L2 issue 数量；
- revision 请求、成功、耗尽轮次。

Metrics 只用于聚合，不承担单次请求诊断；单次请求必须通过日志和 Trace 定位。

## 10. 实现顺序

M2.1 开发时一次只完成一个步骤。每一步完成独立测试和变更总结后停止，未验收不得提前实现下一步。

### 第一步：冻结行为基线与事件字段

产出：

- 固定 M2 成功、CLARIFY、Interpreter 失败、Constraint 失败和 legacy 修订样本；
- 事件名称、字段白名单、脱敏规则和 label 基数清单；
- 观测开启/关闭的业务等价断言。

本步不得增加运行时埋点。

### 第二步：请求根 Trace 与关联上下文

产出：

- `workflow.request` 根 Span；
- 业务 `trace_id` 与 `otel_trace_id` 的稳定关联；
- logger context 自动绑定请求/会话身份；
- LLM Span 成为 Interpreter 或 Planner Span 的子节点。

本步不得记录新的业务产出内容。

### 第三步：M2 阶段边界与产出摘要

按 G0、Interpreter、ConstraintService、ReadinessEvaluator、Router、State 顺序增加 `started/completed/failed` 事件和 Span。

产出：

- 每一步的耗时、结果计数、版本和决策代码；
- CLARIFY 的 blocker codes/IDs；
- Router 的 reason codes 和 required capabilities。

所有摘要在 application 边界生成，不修改领域服务判断。

### 第四步：结构化错误链与失败状态

产出：

- CLI 和日志中的安全 `WorkflowErrorPayload`；
- `cause_type`、upstream refs 和 retryable；
- `TripState.last_error` 写入与状态持久化失败保护；
- 未知异常的统一安全分类。

本步不得改变原始异常是否抛出、退出码和状态转换目标。

### 第五步：legacy Critic 与修订原因

产出：

- L1/L2 分源问题计数和 issue refs；
- `legacy_revision_requested/completed/exhausted` 事件；
- 可安全查看的修订原因摘要或摘要引用；
- 计划内容不进入日志的回归测试。

本步不得修改 Critic Prompt、解析规则、pass/fail 结果或修订轮次。

### 第六步：CLI、JSON 日志与 Console Span 分流

产出：

- 人类可读输出、JSONL 日志、Trace 的明确输出通道；
- 本地日志级别和 Console exporter 开关；
- PowerShell 启动场景的可读输出验证；
- 运行产物忽略规则。

本步不得引入 API、前端或远端观测服务。

### 第七步：Metrics 与基数保护

产出：

- M2 stage、route、error、LLM、legacy review/revision 聚合指标；
- label allowlist 和高基数拒绝测试；
- Metrics 采集失败不改变业务结果的测试。

### 第八步：端到端验收与交接

产出：

- 同一 `trace_id` 的成功、CLARIFY、失败、Critic 修订完整事件序列；
- 观测前后业务输出、异常、状态、调用次数等价报告；
- 脱敏检查、性能开销和未解决风险；
- M2.1 完成报告与 M3 非影响声明。

## 11. 测试矩阵

### 11.1 单元测试

- event envelope 必填字段、枚举和时间；
- logger context 绑定与清理，防止请求间串线；
- WorkflowError 安全序列化；
- stage summary 白名单；
- Prompt、响应、完整计划、Key、PII 不进入日志；
- issue ref 稳定且不能反推原文；
- Metrics label 基数限制；
- observer/exporter 失败产生安全告警但不改变业务结果。

### 11.2 集成测试

- G0 → Interpreter → Constraint → Readiness → Router → State 共用请求上下文；
- LLM Span 是 Interpreter/Planner 的子 Span；
- CLARIFY 事件可定位具体 blocker code；
- Interpreter Schema 失败可定位 `stage/category/code/cause_type`；
- Constraint 归一化失败保留原始 `WorkflowError` 根因；
- legacy L2 问题触发修订时可关联 review 和 revision；
- 修订耗尽进入 FAILED，未被记录为成功。

### 11.3 E2E 与行为等价

对固定输入比较观测改造前后：

- RouteDecision、ClarificationRequest、ConstraintSnapshot 等价；
- 成功返回、失败异常、CLI 退出码一致；
- TripState 目标状态一致，仅允许既有 `last_error` 在失败时被填充；
- Prompt 内容和版本一致；
- LLM 调用次数、模型、retry_count 一致；
- 不产生地图、酒店、航班、门票等 M3 工具调用；
- 日志可从 `workflow_started` 追踪到 `workflow_completed` 或 `workflow_failed`。

M2.1 不新增独立 Live LLM 质量门。既有 M2 Live Gate 继续有效；如授权执行一次真实 Smoke，只用于确认 Trace 关联和脱敏，不重新评判 Prompt 质量，也不得因观测失败切换 Fake。

## 12. 阶段验收门

- [ ] 一个请求的应用日志、LLM Span、路由结果和错误共享可关联的 Trace；
- [ ] G0、Interpreter、Constraint、Readiness、Router、State 都有阶段状态和安全产出摘要；
- [ ] `WorkflowError` 的 stage/category/code/safe_message/retryable/upstream refs 可定位；
- [ ] CLARIFY 可看到 blocker codes/IDs 和 Router reason codes；
- [ ] legacy Critic 触发修订时可看到 L1/L2 来源、issue refs 和修订轮次；
- [ ] Console Span 不再淹没人类可读 CLI 输出；
- [ ] 日志不含完整输入、Prompt、LLM 响应、计划、PII 或凭证；
- [ ] 观测开启/关闭的业务结果、异常、状态、Prompt 和调用次数等价；
- [ ] 没有修改 M3+ 契约、业务代码或验收标准；
- [ ] 默认测试零网络，strict/fail-fast 语义不变；
- [ ] 单元、集成、E2E、脱敏和行为等价测试通过；
- [ ] `git diff --check`、覆盖率和既有 M2 回归通过。

## 13. 允许修改范围

- `src/obs/` 或迁移后的 `src/infrastructure/observability/`；
- `main.py`、本地 CLI/组合根中的观测装配；
- `src/application/interaction_facade.py` 的边界埋点和错误记录；
- DeepSeek Gateway 的关联字段，不改变请求参数和错误传播；
- `src/engine/loop.py`、`src/review/l2.py` 的 legacy 审计埋点；
- 与上述变更直接对应的测试、Fixture、评测报告和文档；
- 必要的 `.gitignore` 运行日志规则。

如果实现需要修改 RequestInterpreter、ConstraintService、ReadinessEvaluator、InteractionRouter，只允许无业务判断的 Span 包装；优先在 Facade 边界完成，不得修改 Prompt、Schema、归一化或路由代码。
