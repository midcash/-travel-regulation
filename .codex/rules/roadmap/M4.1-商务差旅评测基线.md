# M4.1：商务差旅评测基线

> 文档状态：Frozen v1.0，可编写并执行阶段 Plan  
> 前置阶段：M4 已完成且历史验收保持不变  
> 后续阶段：M4.2 差旅语义与能力路由  
> 本阶段性质：评测基础设施与改造前基线，不修改生产业务语义

## 1. 阶段定位

M4.1 只建立商务差旅改造所需的统一评测标尺，并保存 M4 当前实现的改造前结果。它回答三个问题：

1. 商务差旅请求应当产生哪些可观察结果；
2. 当前系统在哪一层、以何种方式失败；
3. M4.2、M4.3 及后续阶段是否在同一组冻结样本上产生了可量化提升。

本阶段不以“让业务案例通过”为目标。历史实现对差旅场景得分较低是预期事实，只要评测器能够稳定、准确地暴露该差距，就属于有效基线。

```text
冻结 Golden Cases 与 Oracle
→ 运行当前 M4 系统
→ 捕获各阶段结构化产出
→ 确定性评分与失败归因
→ 固化 M4-before 报告
→ 为 M4.2/M4.3 提供同一把尺子
```

## 2. 阶段目标

本阶段必须完成：

- 冻结第一版商务差旅 Golden Dataset、Schema、数据卡和 SHA-256；
- 建立可版本化的 Agent 运行结果、逐案例评分、阶段分数卡和差异报告合同；
- 建立无需网络即可重复运行的 Offline Eval；
- 建立受预算控制的 Live LLM Baseline，用于观察真实 Interpreter/Router 行为；
- 保存 M4-before 原始结果、汇总指标和开发者主审/Reviewer Agent 复审记录；
- 将失败归因到 Interpreter、Scope、Router、Task Graph、Evidence、Candidate、Plan 或 Delivery 层；
- 提供后续阶段统一调用的评测入口与机器可读报告。

本阶段完成后，只能宣称“商务差旅评测基线已建立”，不得宣称差旅语义、政策检索或端到端流程已经完成。

求职优先裁剪原则：M4.1 只建设后续 M4.2～M5 会直接复用的 Case Registry、确定性评分、Offline/Live 双轨 Runner、Artifact 和 diff；不建设通用评测平台、Web 控制台、分布式执行、在线实验或生产发布系统。

## 3. 明确不做

M4.1 禁止实现或修改：

- `MeetingRequirement`、`BusinessTripScope` 或会前住宿需求的生产计算；
- `RequestInterpreter` 的差旅类别、Prompt 或输出合同；
- `InteractionRouter` 的能力映射；
- Task Graph 的差旅阶段扩展；
- `PolicyKnowledgePort`、PDF Adapter 或完整 RAG；
- 航班、酒店、市内交通真实 Adapter；
- Composer、Schedule、Budget、Gate、Critic 或 Repair 的业务修复；
- 为提高基线得分而改变生产代码、Fixture 或期望结果；
- 在本 Spec 冻结前提前编写或执行阶段 Plan；冻结后由独立 Plan 文档实施。
- 重新开展完整地基模型选型、训练或微调；
- 登录系统、员工档案、员工等级与个性化政策匹配；
- 用户模拟器、多轮对抗、多 Agent 协作损耗评测；
- A/B、灰度发布、线上真实流量监控和回滚系统。

当前 DeepSeek Gateway 作为既有工程基线继续使用，但 M4.1 不在 Spec 中固定具体模型 ID。Live 运行必须显式读取环境变量 `DEEPSEEK_MODEL`；缺失或空值时进入配置失败，禁止静默使用历史默认 `deepseek-chat`。只有模型选型成为独立目标时，才在冻结业务私有集上比较结构化成功率、专项能力、延迟、成本与隐私约束；公开榜单不能替代业务终审。

## 4. 评测对象与边界

### 4.1 产品 Oracle

评测使用项目总 Spec 已冻结的 `meeting_arrival_ready` 作为业务 Oracle：

- 首版只覆盖中国大陆境内、单人、单出发城市、单目的城市和首场会议；国际/港澳台、多旅客和多城市请求返回 `UNSUPPORTED_SCOPE`；
- 规划范围从出发地开始，终止于首场会议的 `required_arrival_at`；
- 默认关注通用公司政策、去程航班或城际交通、方案所需的一晚会前住宿和到会场的必要市内交通；
- 系统可以同时比较“前一日到达并住宿”和“会议当日凌晨到达并直达会场”等可行方案；
- 会议结束时间、会议期间住宿、会后住宿和返程不属于首版规划范围；
- 返程默认 `not_planned`，但必须显式披露；
- 景点、活动、门票和娱乐不得进入主链路；
- 证据不足、能力缺失或硬约束无法满足时必须澄清、失败或返回不支持，不能输出伪完整方案。

本节只定义评分标准，不授权 M4.1 把这些规则写入生产路径。

### 4.2 被评测层级

每个案例至少观察以下层级：

```text
request
→ interpreter
→ scope
→ router
→ task_graph
→ evidence
→ candidate_pool
→ plan
→ delivery / workflow_error
```

当前 M4 不存在 `scope` 产出时，必须记录为 `MISSING_STAGE_OUTPUT` 或对应业务缺失，不得由评测器合成一个成功结果。

### 4.3 Offline 与 Live 的职责

- **Offline Eval**：通过公开 Use Case/Facade 运行当前完整 M4 链路；Interpreter、Composer 和工具均使用显式 Fake、固定 Clock、固定 Fixture 与故障注入，验证评测器、评分器、错误传播、M4 当前纵向行为与结果可重复性；普通 CI 零网络。
- **Live Semantic Baseline**：只有 `RequestInterpreter` 使用通过 `DEEPSEEK_MODEL` 显式配置的真实 DeepSeek 模型；Constraint、Readiness 和 Router 使用当前确定性实现，Composer 与所有外部工具均不得启动。该基线只观察真实语义解释、澄清和能力路由行为。
- M4.1 不运行真实工具 E2E。真实工具与完整纵向切片属于 M4.3。
- M4.1 不运行真实 Composer。真实 Composer 与真实政策、去程、酒店和市内交通共同组成的 Live E2E 属于 M4.3。

Live 失败不得切换到 Fake 后标记通过。外部模型不可用应记录为 `EXTERNAL_DEPENDENCY_FAILURE`，并保留失败报告。

### 4.4 评测分层与执行顺序

商务差旅改造采用“组件级先行、阶段集成级收尾、跨阶段持续扩大”的评测方法：

```text
业务北极星与失败模式
→ 组件指标与评分合同
→ 按指标标注案例和 Oracle
→ Component Eval
→ Stage Integration Eval
→ baseline/current/diff
→ Stage Gate
```

指标必须先于数据标注。Golden Dataset 中每个期望字段和评分规则都必须能够追溯到某个组件合同、集成不变量或业务北极星指标；禁止先生成大量样本，再根据已有数据临时发明指标。

两级评测职责如下：

- **Component Eval**：隔离 Interpreter、ScopeResolver、Router、Task Graph、Policy Retrieval、Tool Adapter、Candidate/Planner/Composer 等组件，识别各组件特有的失败模式；
- **Stage Integration Eval**：通过公开 Use Case/Facade 连接本阶段已实现组件，检查跨模块合同、关键轨迹和终态，不用下游成功掩盖上游错误；
- **Release Gate**：由 M6 汇总已成熟的组件与阶段集成评测，再增加 P95 延迟、Token/成本、最大步骤、安全和复现性门槛，不在 M4.1 提前建设完整上线体系。

每个后续阶段都必须先通过本阶段 Component Gate，才能运行 Stage Integration Gate；项目未收尾不是推迟集成评测的理由。M4.1 自身同时建立现有组件基线和一条 M4-before 完整但全离线的集成基线。Live Semantic Baseline 使用独立分数卡，不得与 Offline Integration 指标合并为单一总分。

## 5. 数据集规格

### 5.1 数据集身份

首版正式验收集和开发集固定标识为：

```text
dataset_id = business-travel-m4.1-v1
dev_dataset_id = business-travel-m4.1-dev-v1
```

数据集必须包含：

- `dataset.jsonl`：案例与机器可判定 Oracle；
- `dataset-card.md`：目的、边界、来源、许可、限制、隐私和已知偏差；
- `SHA256SUMS` 或等价 manifest：文件 hash、Schema 版本和生成时间；
- 审查记录：开发者主审、独立 Reviewer Agent 复审、争议裁决和最终结论。

一旦 M4-before 正式运行，案例正文与 Oracle 冻结。后续修订必须新建数据集版本，不得原地修改历史分数。

### 5.1.1 数据集审查与裁决

本项目为个人求职项目，不要求虚构第二位人工审查者。首版 Golden Dataset 采用：

```text
开发者主审
→ 独立 Reviewer Agent 结构化复审
→ 开发者对争议作最终裁决
→ 冻结 Dataset 与审查记录
```

- 开发者主审业务意图、输入真实性、Oracle、边界条件和敏感信息；
- Reviewer Agent 只检查总 Spec/M4.1 一致性、Oracle 歧义、覆盖缺口、标签错误、泄漏风险和评分可执行性；
- Reviewer Agent 不得直接修改 Dataset、Oracle、Fixture 或 hash manifest，只能输出结构化问题；
- 每条 Reviewer 问题必须由开发者裁决为 `accepted`、`rejected` 或 `revised`，并记录理由；
- `accepted` 或 `revised` 问题未关闭前不得冻结数据集；`rejected` 必须具有可审计理由；
- 审查记录至少包含 reviewer 类型、实际模型/版本、Prompt/审查规则版本、时间、涉及的 `case_id`、问题类别、结论和裁决；
- 若运行环境无法提供独立 Reviewer Agent，本阶段不得把开发者自审两次包装成复审通过，应记录 `REVIEW_GATE_INCOMPLETE` 并阻断冻结。

“独立”指 Reviewer Agent 不读取开发过程中的期望答案推导过程，只读取待审数据、数据卡和权威 Spec；它不得与生成或修改该批 Golden Cases 的 Agent 使用同一会话上下文。最终业务责任仍由开发者承担，Agent 复审不等于第二位人工专家背书。

### 5.2 样本规模与覆盖

正式验收集固定为 12 条经过开发者主审和独立 Reviewer Agent 复审的案例；开发集固定为 6 条，可用于实现、调试和 Prompt 迭代。两者可以覆盖同一行为类别，但不得复用相同输入文本。12 条正式案例通过多标签覆盖以下行为切片：

1. 当日可达且无需住宿；
2. 为按时参会必须提前一晚；
3. 同一请求同时存在“前一日到达并住宿”和“当日凌晨到达并直达会场”的可行候选；
4. 跨午夜航班或城际交通；
5. 会议地点缺失，需要 G1 澄清；
6. 会议时间或时区冲突；
7. 公司政策限制去程费用或酒店价格；
8. 酒店每晚价、含税价和总价语义区分；
9. 需要会前住宿的候选无可用酒店，但无住宿候选仍独立判定；
10. 机场/车站至酒店或会场路线不可达；
11. 政策证据冲突或过期；
12. 用户明确要求返程但 MVP 不支持；
13. 供应商超时、空结果和非法 Schema；
14. 原 M4“只有交通候选”的回归案例；
15. 请求包含景点或活动时，不应把它们纳入差旅主链路。

### 5.3 数据隔离

- Golden Dataset 不得用于修改 Prompt 时的逐条拟合；
- `business-travel-m4.1-dev-v1` 与 `business-travel-m4.1-v1` 必须分文件、分 hash 和分报告；
- 如果根据某条正式失败案例修复实现，该案例及 Oracle 仍保留；修复时优先向开发集增加同类变体，防止只记住正式文本；
- Live 输入不得包含真实公司、真实员工、联系方式、证件或未脱敏行程。

### 5.4 案例注册表与评测视图

首版使用“一个规范化 Case Registry，多个只读 Eval View”，不为每个组件复制并逐渐分叉一套业务样本：

```text
BusinessTravelCaseRegistry
├─ interpreter_view
├─ scope_router_view
├─ task_graph_view
├─ policy_retrieval_view
├─ tool_calling_view
├─ planner_composer_view
└─ stage_e2e_view
```

同一 `case_id` 可以出现在多个视图中，但每个视图使用独立 Oracle。例如同一个“次日上午参会”案例，可以分别检查会议字段、差旅范围、能力集合、任务依赖和最终 meeting-arrival-ready 结果。组件不适用的 Oracle 必须显式标记 `not_applicable`。

评测资产分为两类：

- **test files**：pytest 中的确定性 Schema、边界、不变量和故障注入测试；
- **evalset**：Agent 语义行为、组件质量、跨模块轨迹、端到端结果、成本和稳定性评测。

两者可以引用同一 Fixture 或 `case_id`，但不得用 JSONL Eval 取代单元测试，也不得用 pytest 的“无异常”取代业务质量评分。

### 5.5 准时参会时间策略

首版 Golden Oracle 统一引用版本化策略：

```text
timing_policy_id = timing-policy-cn-domestic-v1
meeting_arrival_buffer_minutes = 30
airport_exit_buffer_minutes = 45
railway_exit_buffer_minutes = 20
local_transport_risk_buffer_minutes = 20
```

该策略是求职版项目用于复现和比较的评测基准，不宣称为行业统一标准。所有时间先转换为目的地时区，再执行确定性计算。国内航班与铁路候选分别使用对应的离站 buffer；市内交通风险 buffer 对“到达机场/车站至会场”的整条必要路线增加一次，不按路线分段重复累加。

对直接前往会场的去程候选，定义：

```text
required_arrival_at
  = meeting_start_at - meeting_arrival_buffer

candidate_ready_at
  = scheduled_arrival_at
  + airport_or_railway_exit_buffer
  + local_route_duration
  + local_transport_risk_buffer

same_day_attendance_feasible
  = candidate_ready_at <= required_arrival_at
```

边界相等视为可行。首版不额外引入历史误点概率、天气概率或供应商未提供的随机风险估算；若动态证据明确给出延误后的预计到达时间，则应把该时间作为 `scheduled_arrival_at` 的受控替代事实并保留 Evidence 引用。

该规则冻结每个去程方案能否满足会议到达时限，以及该方案是否需要一晚会前住宿。会议结束时间和会议期间住宿不进入首版 Oracle。

每个涉及时间可行性或住宿夜的案例必须记录 `timing_policy_ref`。评测运行必须将实际使用的策略 ID、策略内容 hash 和目的地时区写入结果；不得在不升级策略版本和数据集版本的情况下修改数值。

### 5.6 会前住宿策略

首版 Golden Oracle 统一引用版本化策略：

```text
lodging_policy_id = pre-meeting-lodging-policy-v1
derivation_basis = selected_outbound_candidate + first_meeting_required_arrival_at
date_basis = destination_local_date
max_pre_meeting_nights = 1
```

会前住宿是**方案级条件**，不是请求级统一结论。对每个去程候选分别判断：

1. 将首场会议开始时间转换到目的地时区，并用 `timing-policy-cn-domestic-v1` 得到 `required_arrival_at`；
2. 若候选在会议本地日期当日出发，且经离站、市内路线和风险 buffer 后仍能在 `required_arrival_at` 前到达，则该方案不需要酒店；
3. 若候选在会议前一日本地日期到达，且方案选择在目的地过夜，则该方案需要首场会议前一晚的酒店；
4. 首版最多规划一晚会前住宿；更早到达、会议期间住宿、会后住宿和多夜连续住宿均不进入 Oracle；
5. 同一请求允许一部分候选需要酒店、另一部分候选无需酒店，评测不得把 `stay` 简化为请求级永久必选或永久排除；
6. 需要酒店的候选必须具有酒店 Evidence、入住/退房日期、酒店至会场路线和价格；该酒店失败只淘汰受影响候选，不得错误淘汰独立可行的无住宿候选；
7. 若所有去程候选均不可在范围内形成 meeting-arrival-ready 方案，则返回无可行方案，不得扩展到多夜住宿制造成功。

形式化表示为：

```text
pre_meeting_night
  = first_meeting_local_date - 1 day
    iff selected_outbound_candidate arrives on the previous local date
    and the plan includes an overnight stay

candidate_pre_meeting_lodging
  = [] or [pre_meeting_night]
```

例如首场会议为周六 09:00：周五到达并住宿的方案包含周五夜酒店；周六凌晨到达且能够满足 buffer 的方案不包含酒店。两者可以作为不同方案同时进入比较。

该策略只适用于首场会议前的抵达规划。跨天连续会议可以提供首场开始时间作为规划目标，但会议期间住宿和后续会议不进入首版结果；用户明确要求完整多日住宿时，应返回范围说明，不得静默声称已经覆盖。

每个涉及住宿的案例必须记录 `lodging_policy_ref`。评测运行必须记录策略 ID 与策略内容 hash；策略数值、边界或适用范围变化时，必须同时升级策略版本和数据集版本。

### 5.7 会议字段最小精度与 G1 Oracle

首版 Golden Oracle 统一引用：

```text
meeting_readiness_policy_id = meeting-readiness-policy-v1
```

启动任何外部研究任务前，以下字段必须达到可确定性计算的精度：

```text
origin
meeting_city
meeting_local_date
meeting_start_time_to_minute
meeting_timezone
traveler_count
geocodable_meeting_venue
```

首版旅行者规则冻结为：第一人称单数表达（如“我”“本人”）确定性归一化为 `traveler_count=1`；明确多人请求返回 `UNSUPPORTED_SCOPE`；无法判断人数时进入 CLARIFY。首版不规划团体票、多人房间或同行者偏好。

会议开始时间必须精确到分钟。仅有“上午”“下午”“晚上”“午后”等时段表达不满足要求，禁止自动映射为 09:00、14:00 等默认时间。目的地时区必须可唯一确定；若城市与显式时区冲突或存在无法消解的歧义，则进入澄清。

会议地点必须至少达到可唯一地理编码的粒度，允许：

- 具体地址；
- 明确且可唯一解析的 POI；
- 在会议城市内可唯一解析的会场名称。

仅提供城市、行政区、商圈、“市中心”、“某酒店”“某园区”等不能唯一定位的描述不满足要求。M4.1 Offline 使用 Fixture 给出地理编码唯一、多义或无结果，评测器不得通过模型常识判断唯一性；M4.2/M4.3 可以执行受控 `venue_resolution` 输入验证，但在地址唯一前政策、去程、酒店和市内交通研究调用数必须为零。

任一字段缺失、冲突或精度不足时，Oracle 固定为：

```text
expected_terminal_status = CLARIFYING
expected_mode = CLARIFY
expected_capabilities = []
expected_external_research_task_count = 0
```

澄清结果必须指出具体 blocker 及其对参会可行性的影响；不得先查航班、酒店、政策或地图再补问。用户提供分钟级开始时间、明确时区和可唯一地理编码地点后，才允许冻结会议要求并进入 PLAN 研究链路。

该策略只定义新建差旅 PLAN 的 G1 最小精度，不提前定义 REFINE、COMPARE、REPLAN 或多轮状态继承规则。每个相关案例必须记录 `meeting_readiness_policy_ref`，运行结果记录策略 ID 与 hash；策略变化必须升级策略和数据集版本。

### 5.8 通用差旅政策边界

M4.1～M4.3 首版只采用一份对所有用户同样适用的通用差旅政策：

```text
policy_applicability_id = universal-business-travel-policy-v1
applicability = all_users
employee_grade_dimension = not_supported
identity_policy_join = out_of_scope
```

系统不实现员工等级、部门、职位、租户或个人例外与政策条款的匹配，也不要求用户提供这类信息。Golden Case 不得因缺少员工档案或等级进入 CLARIFY；政策 Agent 面向所有案例检索同一份版本化 PDF，获取去程费用上限、单晚酒店上限、会议最小提前到达时间、本地交通许可及页码证据。

该简化不等于把政策内容硬编码到 Fixture 或 Prompt。Fixture 只固定政策文档身份、版本、hash 和预期检索条件；具体规则仍必须由 `PolicyResearchAgent → PolicyKnowledgePort → PDF Adapter/RAG` 检索并形成 `PolicyRule + PolicyEvidence`。检索不到条款、条款冲突、版本过期、引用错误或解析失败仍按政策检索/证据失败处理。

后续可选优化可以引入登录系统和员工信息，并执行：

```text
authenticated_employee_profile
+ versioned_policy_catalog
→ applicable_employee_policy
→ transport / stay / local transport planning
```

该扩展必须另立阶段和 Spec，并增加身份、租户隔离、政策适配和隐私评测；不得提前进入 M4.1 数据集、组件、指标或验收条件。

每个政策相关案例必须记录 `policy_applicability_ref`，运行结果记录 applicability ID 与 hash。首版禁止出现 `traveler_policy_grade`、`employee_grade` 等影响 Oracle 的字段。

## 7. 技术选型

### 7.1 评测框架

- 语言与模型：Python 3.11+、Pydantic v2；
- 数据格式：JSONL 保存案例，JSON 保存逐次运行和汇总，Markdown 保存面向人的报告；
- Hash：Python 标准库 `hashlib.sha256`；
- 测试：pytest；
- 评分：优先确定性评分器，不在 M4.1 引入 LLM-as-a-Judge；
- 时间：所有评测通过固定 `Clock`；
- 入口：在现有 `evaluation/` 基础上抽取可复用 Runner/Scorer/Reporter，保留 M0 入口兼容性。

选择确定性评分器的理由是当前目标主要为结构化语义、能力集合、依赖关系、失败类型和证据覆盖；这些均可精确判定。只有 M5 的语义体验质量超出确定性规则表达能力时，才评估独立 Critic 或 Judge。

### 7.2 Runner 约束

Runner 必须：

- 通过公开 Use Case/Facade 运行系统，不直接调用私有函数拼装高分；
- 支持按 dataset、case_id、tag、运行模式筛选；
- 每个案例隔离状态并固定随机性、时间、Fixture 和预算；
- 捕获所有规定阶段的结构化输出与错误；
- 单案例异常不得中断整批运行；
- 评测器自身异常必须分类为 `EVALUATOR_ERROR`，不得计为业务失败；
- 输出不可变 run artifact，并支持 baseline/current/diff。

Live Semantic Baseline 使用公开只读的 `SemanticEvaluationUseCase`：执行 G0、真实 Interpreter、Constraint、Readiness 和 Router 后立即停止；不持久化正式 Trip State，不调用 Planner、Task Graph、Composer 或工具。评测器不得通过依次调用这些组件的私有函数拼装高分。

### 7.3 Live 模型配置与可比性

Live Runner 的模型身份由运行时环境决定：

```text
provider = deepseek
model = required(DEEPSEEK_MODEL)
missing_or_blank_model = CONFIGURATION_ERROR
implicit_model_fallback = forbidden
```

`deepseek-v4-flash` 只是当前环境可能配置的模型值，不是写死在评测代码或 Spec 中的永久模型。历史默认 `deepseek-chat` 不属于 M4.1 的合法隐式默认；若操作者确实要使用某个模型，必须通过环境配置显式声明。

为了兼顾求职版的可复现性和跨阶段可比较性，报告拆分四类不含凭证的 fingerprint：

```text
runtime_fingerprint
  = provider + model + base_url_fingerprint + timeout + sampling + retry + seed_status

dataset_fingerprint
  = dataset_id + dataset_hash + oracle_version

view_fixture_fingerprint
  = 当前评测视图实际读取的 Fixture hash 集合

policy_fingerprint
  = timing + lodging + meeting_readiness + policy_applicability + repetition
```

不得把所有未来 Fixture 汇总为一个全局 hash。比较某项指标时，只要求该指标依赖的 fingerprint 一致；M4.3 新增政策或酒店视图不得使 M4.2 语义视图自动失去可比性。任何 fingerprint 均不得包含 API Key、Token 或完整 URL 查询参数。

Prompt、Schema、代码 commit 和阶段名称属于被测版本，必须在报告中单独记录，但不纳入控制变量 fingerprint。这样 M4.2 可以通过修改 Prompt、Schema 或代码产生正式 diff，同时仍能证明模型和外部评测条件没有变化。

差异报告规则如下：

- baseline 与 current 的相关 fingerprint 相同，才允许输出该视图可归因的正式提升/退化结论；
- 任一相关 fingerprint 不同仍可保存单次报告，但该视图 diff 状态必须为 `NON_COMPARABLE_CONFIGURATION`，不得用于 Stage 提升结论；
- 如果更换模型后仍需建立正式纵向比较，必须用新控制配置分别重跑修改前和修改后版本，形成新的 baseline series；
- 模型、供应商或采样条件变化带来的分数变化不得归因为 M4.2/M4.3 代码改进。

### 7.4 统一验收命令合同

M4.1 实现后必须提供单一阶段验收入口：

```powershell
venv/Scripts/python -m evaluation.stage_acceptance --stage M4.1 --mode all
```

其中 `all` 依次执行 Dataset 校验、Offline Component Eval、Offline Stage Integration Eval、M4-before 生成、diff 自比较和 Live Semantic Baseline；只有本次全部步骤成功才返回零退出码。普通零网络开发与 CI 使用：

```powershell
venv/Scripts/python -m evaluation.stage_acceptance --stage M4.1 --mode offline
```

Live 运行状态必须区分：

```text
LIVE_ATTEMPT_RECORDED
  = 无论成功或外部失败，均保存脱敏运行报告

LIVE_BASELINE_SUCCESS
  = 全部规定 Live 案例按冻结配置完成并生成完整指标
```

缺少密钥、缺少显式 `DEEPSEEK_MODEL`、超时、限流或供应商错误必须生成失败报告并返回非零；不得静默跳过、减少案例、切换 Fake 或回退到 `deepseek-chat`。`LIVE_ATTEMPT_RECORDED` 只证明 fail-fast 与失败可观察，不满足首次阶段验收。

首次完成 M4.1 必须存在一份 `LIVE_BASELINE_SUCCESS` artifact，且其 `system_commit`、`dataset_fingerprint`、`runtime_fingerprint` 和相关 view/policy fingerprint 与本次待验收版本匹配。正式 `--mode all` 在启动时要求源码工作区干净；报告输出目录不参与 dirty 判断。脏工作区只允许生成 `source_tree_status=dirty`、`source_diff_hash` 和 `run_status=NON_ACCEPTANCE_RUN` 的临时报告，并返回非零，不得生成正式基线。`--mode all` 不得用旧 artifact 掩盖本次 Live 失败。

统一入口的实现细节由 Plan 拆解，但命令、退出码、Live 状态和报告索引属于本阶段公开合同。

## 8. 指标与失败归因

### 8.1 核心指标

M4.1 建立并报告以下指标，但不要求当前 M4 达到业务通过阈值：

- `mode_accuracy`；
- `clarification_precision`、`clarification_recall`；
- `scope_exact_match`；
- `capability_exact_match`；
- `task_dependency_accuracy`；
- `candidate_pre_meeting_lodging_exact_match`；
- `alternative_diversity_pass_rate`；
- `recommendation_grounding_rate`；
- `evidence_coverage`；
- `candidate_coverage`；
- `meeting_arrival_feasibility_accuracy`；
- `return_scope_disclosure_rate`；
- `forbidden_output_rate`；
- `failure_semantics_accuracy`；
- `schema_valid_rate`；
- `p50/p95_latency_ms`、调用数、Token 与估算成本。

集合精确匹配定义为：

```text
exact_match = 1 iff predicted_set == expected_set else 0
```

关键能力不得只计算宽松 recall，因为额外调用无关能力同样是路由错误。

### 8.2 组件级与集成级指标归属

M4.1 冻结以下指标归属，后续阶段只能在版本化 Spec 中调整：

| 评测视图 | 主要失败模式 | 核心指标 |
|:---|:---|:---|
| Interpreter | 字段遗漏、否定失真、时区错误、无效澄清 | field precision/recall、clarification precision/recall、Schema valid rate |
| Scope/Router | required 能力漏选、无关能力多选、reason 缺失 | scope exact match、capability exact match、reason coverage |
| Task Graph | 节点遗漏、依赖倒置、越权启动、预算失控 | task dependency accuracy、trajectory validity、step/tool-call count |
| Policy Retrieval | 漏召回、错引页码、无依据规则、无答案不拒答 | Recall@k、citation accuracy、rule faithfulness、no-answer accuracy |
| Tool Calling | 工具选错、参数错误、Schema/字段语义错误 | tool selection accuracy、argument accuracy、Schema valid rate、normalization accuracy |
| Planner/Composer | 硬约束遗漏、复制方案凑数、推荐理由无依据、幻觉候选、证据断链、范围误披露 | feasibility accuracy、alternative diversity、recommendation grounding、illegal reference rate、evidence coverage、disclosure rate |
| Offline Stage Integration | 当前 M4 最终失败、关键轨迹偏离、静默部分成功 | pass@1、trajectory validity、silent partial success rate、normalized result hash |
| Live Semantic Integration | Interpreter 输出波动、澄清或路由不稳定、非法启动下游 | pass@1、pass-all-3、pass-any-3、Schema valid rate、zero downstream calls |

M4.1 只对当前 M4 已存在组件产生基线；尚未实现的 ScopeResolver、Policy Retrieval 和差旅工具视图记录为 `NOT_IMPLEMENTED_IN_BASELINE`，不得记为零分或通过。M4.2、M4.3 分别激活对应视图。

### 8.3 稳定性指标

商务差旅属于用户一次请求就应可靠工作的任务，主指标使用 `pass@1` 和连续 k 次全部成功率，而不是“多试几次至少成功一次”的宽松指标：

```text
pass@1 = 首次运行成功的案例比例
pass-all-k = 所有 k 次重复运行均成功的案例比例
pass-any-k = k 次中至少一次成功的案例比例，仅用于诊断
```

首版稳定性配置冻结为：

```text
repetition_policy_id = repetition-policy-m4.1-v1

offline_full_suite_runs = 2
offline_acceptance = normalized_result_hash_run_1 == normalized_result_hash_run_2

live_blocking_runs_per_case = 3
live_blocking_acceptance = pass-all-3

live_observational_runs_per_case = 1
live_observational_metric = pass@1
live_blocking_case_count = 4
live_observational_case_count_max = 8
live_interpreter_call_budget_max = 20

temperature = actual_sent_value_or_provider_default
seed_status = unsupported
max_tokens = 4096
retry_count = 0
```

Offline Component Eval 与 Stage Integration Eval 必须分别完整运行两次。比较前应从结果中排除 `run_id`、`trace_id`、`started_at`、真实持续时间和报告路径等非确定字段，再对规范化业务结果计算 SHA-256；两次 hash 不一致即为离线复现失败。该检查证明固定 Clock、Fixture、配置和实现下的确定性，不称为模型稳定性。

Live Semantic Baseline 只对带 `blocking_live_stability` 标签的小型语义子集执行每案例三次，并报告 `pass@1`、`pass-all-3` 和诊断性 `pass-any-3`。其他观察案例每案例只运行一次，只报告 `pass@1`，不得混入 `pass-all-3` 分母。阻断子集必须覆盖至少一个能够路由至 PLAN 的完整语义输入、一个必要澄清、一个否定/排除表达和一个住宿范围相关表达；具体 case_id 在数据集审查时冻结。这里的“完整 PLAN”只表示 Interpreter、Constraint、Readiness 和 Router 输出完整，不授权启动 Task Graph、Composer 或任何工具。

Live Runner 显式覆盖项目默认值并发送 `max_tokens=4096`。`temperature` 必须记录实际发送值；若所选模型路径未显式发送，则记录 `provider_default`，不得虚报为 0。接口未提供项目可验证的 seed 时记录 `seed_status=unsupported`。Token 必须使用供应商 usage；成本只有存在版本化模型价格配置时才计算，否则记录 `UNAVAILABLE_WITH_REASON`。timeout、调用预算、模型、Fixture、Clock 与采样配置作为控制变量冻结。M4.1 只记录 M4-before 的 `pass-all-3`，旧系统未达到业务阈值不导致 M4.1 失败；M4.2 对同一阻断语义子集要求 `pass-all-3=100%`。

如果供应商事实会随时间变化，重复运行必须使用同一 Evidence Fixture；真实动态工具稳定性单独报告，不能与模型推理稳定性混算。外部服务超时或限流按 `EXTERNAL_DEPENDENCY_FAILURE` 单列，不得通过重试或减少分母制造通过。

### 8.4 轨迹评测

集成评测除终态外，还必须检查关键行动路径：

- 关键会议字段缺失时停在 CLARIFY，不启动研究；
- 先冻结 scope，再由 Router 映射能力；
- 住宿和市内交通任务不得早于其依赖事实；
- 计划项只能引用已登记 Candidate/Evidence；
- 缺少关键能力时不得返回正常 Delivery；
- 不得调用景点、返程或其他排除能力。

轨迹评测比较允许的节点、依赖和禁止动作，不要求所有合法实现具有完全相同的内部日志序列。

### 8.5 失败分类

每个案例同时记录三层状态，禁止把“基线业务失败”误写成“评测运行失败”：

```text
run_status
  = COMPLETED | EXTERNAL_FAILURE | EVALUATOR_ERROR | NON_ACCEPTANCE_RUN

component_availability
  = IMPLEMENTED | NOT_IMPLEMENTED_IN_BASELINE | NOT_APPLICABLE

business_assertion
  = PASS | FAIL | NOT_SCORABLE
```

当前 M4 没有 ScopeResolver 时，Scope 组件视图标记 `NOT_IMPLEMENTED_IN_BASELINE` 且不进入组件指标分母；但 Stage Integration 对“缺少必要 Scope 阶段”必须记录 `business_assertion=FAIL`、`first_failed_stage=SCOPE`。`LIVE_BASELINE_SUCCESS` 只表示 Live 运行完整、Artifact 有效且无评测器/外部失败，不表示业务 Oracle 已通过。

第一失败点至少归入：

```text
INPUT_CONTRACT
INTERPRETER
SCOPE
ROUTER
TASK_GRAPH
TOOL_OR_EVIDENCE
CANDIDATE_NORMALIZATION
PLANNING
DELIVERY
EXTERNAL_DEPENDENCY
EVALUATOR
```

禁止使用单一 `FAILED` 或自由文本替代分类。一个案例可以记录多个次级问题，但必须有唯一 `first_failed_stage`。

### 8.6 后续阶段阻断阈值

以下阈值作为 M4.2/M4.3 的共同目标，由后续阶段在同一数据集上证明：

- BLOCKING 合同、Schema 和失败语义：100%；
- `scope_exact_match`：100%；
- `capability_exact_match`：100%；
- `task_dependency_accuracy`：100%；
- 方案级会前住宿、证据覆盖和 meeting-arrival feasibility：100%；
- 冻结成功案例的 `alternative_diversity_pass_rate = 100%`，每份方案至少在去程候选、住宿形态或可验证的时间/价格取舍之一上不同；
- `recommendation_grounding_rate = 100%`，推荐理由只能引用方案字段、政策规则或 Evidence 中可验证的事实；
- `return_scope_disclosure_rate`：100%；
- `forbidden_output_rate`：0%；
- 无未分类异常、无 fallback、无合成成功。
- BLOCKING Live 语义重复运行集 `pass-all-3 = 100%`；
- 关键轨迹合法率 = 100%。

M4.1 自身不因 M4-before 未达到这些业务阈值而失败。

- 总体指标变化；
- 按 tag 的切片变化；
- 新通过、新失败和保持失败案例；
- 第一失败阶段迁移；
- 延迟、Token、成本与调用数变化；
- 退化案例及阻断结论。

## 10. 测试要求

评测系统至少覆盖：

1. 数据 Schema 成功与失败；
2. 重复 `case_id`；
3. 缺失 Oracle 与非法 `not_applicable`；
4. 数据 hash 改变检测；
5. 集合、时间、方案级会前住宿、方案差异、推荐理由依据和失败语义评分器；
6. `timing-policy-cn-domestic-v1` 的航班、铁路、边界相等、跨日和目的地时区计算；
7. `pre-meeting-lodging-policy-v1` 的前一日住宿、当日直达、候选隔离和最多一晚边界；
8. `meeting-readiness-policy-v1` 的分钟级时间、时区、地点唯一性、模糊表达和零研究任务边界；
9. `universal-business-travel-policy-v1` 对所有用户一致适用，且不会因员工等级缺失触发澄清；
10. 单案例异常隔离；
11. evaluator error 与 business failure 分离；
12. 相同输入重复运行的确定性；
13. baseline/current/diff 计算；
14. 脱敏与凭证泄漏检查；
15. 普通 CI 零网络；
16. Live LLM 缺少密钥时显式失败，不切换 Fake；
17. 同一 Case Registry 能生成多个只读评测视图且 Oracle 不串用；
18. Component Eval 失败时 Stage Integration Gate 不得标记通过；
19. `pass@1`、`pass-all-3` 与诊断性 `pass-any-3` 的分母、标签筛选和计算正确；
20. Offline 两次运行的结果规范化、非确定字段排除与 SHA-256 一致性检查正确；
21. 缺失/空 `DEEPSEEK_MODEL` 显式失败且不会回退到 `deepseek-chat`；
22. 控制配置相同允许正式 diff，模型或控制配置不同产生 `NON_COMPARABLE_CONFIGURATION`；
23. Live 成功与外部失败都保存 attempt 报告，但只有完整成功产生 `LIVE_BASELINE_SUCCESS`；
24. `--mode all` 的本次 Live 失败返回非零，且不能被历史成功 artifact 掩盖；
25. 轨迹允许集合和禁止动作评分正确；
26. Live Semantic Baseline 中 Composer、Task Graph 与工具调用数恒为零，且不会生成 Plan/Delivery 作为成功依据；
27. Offline Stage Integration 通过公开 Use Case/Facade 覆盖当前完整 M4 链路，且 Interpreter、Composer、工具均为显式 Fake/Fixture。

测试不能只断言“生成了报告”，必须断言案例数、hash、精确指标、失败类别和第一失败阶段。

## 11. 验收标准

M4.1 通过必须同时满足：

- [ ] 12 条正式 Golden Cases 与 6 条 Dev Cases 分区、分 hash、无重复输入；正式集通过 Schema、开发者主审和独立 Reviewer Agent 复审；
- [ ] 审查记录完整，所有 Reviewer 问题均有 `accepted/rejected/revised` 裁决，未关闭问题为零；
- [ ] dataset card、版本与 SHA-256 完整且可验证；
- [ ] 所有时间可行性案例引用 `timing-policy-cn-domestic-v1`，报告记录策略 hash 与目的地时区；
- [ ] 所有住宿案例引用 `pre-meeting-lodging-policy-v1`，方案级会前住宿 Oracle、来源和策略 hash 完整；
- [ ] 成功案例显式标注最少差异化方案数和允许的推荐依据类型，复制方案改标签不能通过；
- [ ] 所有会议就绪案例引用 `meeting-readiness-policy-v1`；分钟级时间、时区和可地理编码地点边界具有精确 Oracle；
- [ ] 会议 blocker 案例进入 CLARIFY、能力集合为空且外部研究任务数为零；
- [ ] 政策案例统一引用 `universal-business-travel-policy-v1`，所有用户适用同一 PDF 政策；
- [ ] 未实现员工等级、登录身份与个性化政策匹配，且不会因缺少这些信息触发 CLARIFY；
- [ ] 确定性评分器的单元测试覆盖所有 BLOCKING 字段；
- [ ] Component Eval 与 Stage Integration Eval 使用独立分数卡，不合并为无法归因的单一总分；
- [ ] Case Registry 可稳定生成组件、集成评测视图；
- [ ] Offline Component 与 Stage Integration Eval 各完整运行两次，规范化结果 SHA-256 一致；
- [ ] M4-before 对全部案例均产生结果，无中途丢失；
- [ ] 所有失败均有第一失败阶段和分类，无未解释 evaluator error；
- [ ] baseline artifact 不可被 current 运行覆盖；
- [ ] diff 自比较结果为零差异；
- [ ] 存在与待验收 `system_commit + dataset/runtime/view/policy fingerprints` 匹配且 `source_tree_status=clean` 的 `LIVE_BASELINE_SUCCESS` artifact；
- [ ] Live 外部失败保存 `LIVE_ATTEMPT_RECORDED` 报告并阻断本次 `--mode all`，不能替代成功基线；
- [ ] 报告记录模型、版本、配置、时延、Token、成本和失败分布；
- [ ] Live 阻断语义子集按每案例三次报告 `pass@1`、`pass-all-3`、`pass-any-3`，观察集按每案例一次单独报告 `pass@1`；
- [ ] Live Semantic Baseline 只运行真实 Interpreter 与当前确定性 Constraint/Readiness/Router；Composer、Task Graph 和工具调用数均为零；
- [ ] Offline Stage Integration 通过公开 Use Case/Facade 运行当前完整 M4，并显式注入 Fake Interpreter、Fake Composer 与工具 Fixture；
- [ ] 报告记录实际 temperature 或 `provider_default`、`seed_status`、`max_tokens=4096`、timeout、`retry_count=0`、调用预算与重复策略版本；
- [ ] Live 模型只从显式 `DEEPSEEK_MODEL` 读取，缺失/空值失败且无 `deepseek-chat` 回退；
- [ ] 报告记录不含凭证的四类 fingerprint；正式 diff 只比较相关 fingerprint 相同的 baseline/current；
- [ ] `run_status`、`component_availability` 与 `business_assertion` 三层状态准确，未实现组件不会被记为通过或错误进入分母；
- [ ] 默认测试零网络，strict 配置无 fallback/cache/partial success；
- [ ] M0～M4 历史测试继续通过；
- [ ] 未修改生产 Interpreter、Router、Task Graph 或业务规划行为。

阶段验收判断为：

```text
M4.1 Pass
  = Dataset Contract Pass
  + Evaluator Correctness Pass
  + Component Baseline Complete
  + Stage Integration Baseline Complete
  + Offline Determinism Pass
  + M4-before Complete
  + Matching LIVE_BASELINE_SUCCESS Artifact
```

`LIVE_BASELINE_SUCCESS` 不等于 M4-before 已达到后续差旅业务阈值；它表示规定的真实 Agent 行为已完整执行、生成指标并可按统一合同归因。单纯存在 `LIVE_ATTEMPT_RECORDED` 失败报告不能满足本公式。
