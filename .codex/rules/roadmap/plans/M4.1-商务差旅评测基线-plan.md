# M4.1 商务差旅评测基线 Implementation Plan

> 阶段 Spec：`.codex/rules/roadmap/M4.1-商务差旅评测基线.md` Frozen v1.0  
> 前置基线：M0～M4 已验收  
> 目标：建立可复现的 M4-before 商务差旅评测基线，不修改生产业务语义  
> 执行纪律：严格 TDD；每个任务先观察失败测试，再写最小实现，再跑回归  

## 1. 求职优先实施结论

M4.1 只交付五项可在面试中直接演示的能力：版本化 Golden Dataset、确定性 Scorer、公开 Use Case 驱动的 Offline/Live Runner、不可覆盖 Artifact、baseline/current/diff。它不建设通用 Eval 平台，不实现 M4.2 语义修复，不接入 M4.3 的 PDF 或真实旅行工具。

实现完成后，面试演示链为：

```text
同一组冻结差旅案例
→ M4-before 组件分数卡
→ M4-before 全离线集成分数卡
→ Live Interpreter/Router 稳定性报告
→ 第一失败阶段与失败分布
→ 为 M4.2/M4.3 提供可比较基线
```

## 2. 模型路由与工作方式

| 工作 | 推荐模型/强度 | 理由 |
|:---|:---|:---|
| 数据合同、评分器、Runner、Artifact | `gpt-5.6-sol / high` | 跨文件合同与失败语义风险最高 |
| JSONL、Fixture、数据卡机械整理 | `gpt-5.6-luna / medium` | 边界已由本 Plan 冻结，可快速执行 |
| 测试失败定位 | `gpt-5.6-sol / high` | 必须区分 evaluator error 与业务失败 |
| 最终代码 Review | 独立 Reviewer Agent，`gpt-5.6-sol / high` | 检查 Spec 覆盖、数据泄漏和静默放宽 |

若执行环境不能切换模型，则使用当前模型执行，但不得因此改变测试、Oracle 或验收阈值。

## 5. 关键停止条件

出现以下任一情况必须停止并回到 Spec/Plan，不得在代码中临时放宽：

- Golden Oracle 无法确定性评分；
- Reviewer Gate 有未裁决问题；
- Offline Runner 需要调用私有函数才能得到结果；
- 为生成基线必须修改生产 Interpreter/Router/Task Graph/Composer；
- Live 需要回退模型、Fake、重试或减少冻结案例；
- 评测器异常被计成业务失败，或未实现组件被记成通过；
- 正式 Artifact 不能与源码 commit 和四类 fingerprint 绑定。

## 6. M4.1 完成定义

M4.1 完成不表示当前 M4 已经会做商务差旅；它表示“当前不会做什么、首先失败在哪里、后续是否真正提升”已经可以用同一把尺子重复证明。完成后只进入 M4.2，不提前实现 M4.3。
