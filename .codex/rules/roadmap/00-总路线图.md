# 企业商务差旅规划 Agent 求职优先实施总路线图

> 本目录是依据 `.codex/rules/架构.md` 项目总 Spec 分期实施目标架构的执行规格。路线图优先服务于“大模型应用开发”求职展示：先完成可评测、可追溯、可演示的工具型 Agent，再实现交易 Action 与生产韧性。编程 Agent 必须先读项目总 Spec、本文件和当前阶段文件；未经阶段验收，不得进入下一阶段。

## 1. 文档优先级

发生冲突时按以下顺序处理：

1. 当前用户明确要求；
2. `.codex/rules/架构.md`；
3. 本路线图及当前阶段规格；
4. `AGENTS.md`；
5. `evaluation/` 与历史材料。

规格与代码不一致时先报告差异，不得通过修改规格掩盖代码问题。路线图与项目总 Spec 的关系是“分期实现”，延后能力不代表从目标架构删除。

## 2. 规划原则与完成线

### 2.1 优先级依据

按对大模型应用开发岗位的证明力排序：

1. Eval、回归集、失败分析与可量化改进；
2. Tool Use、Grounding、Evidence 与反幻觉；
3. 类型化输出、约束解析、澄清与路由；
4. 动态 Task Graph、有界 Agent 编排与上下文控制；
5. 确定性 Gate、Independent Critic 与 Targeted Repair；
6. Trace、成本、延迟、API、Demo、CI 和复现文档；
7. 多轮状态、计划版本和局部重规划；
8. Action、长期反馈学习和完整生产韧性。

Agent 数量、框架数量和供应商数量不是验收指标。正确性、可解释性、可评测性、失败透明度和工程复现性才是。

### 2.2 求职项目完成线

**M0～M6（包含插入阶段 M4.1、M4.2、M4.3）全部验收通过即达到求职投递标准。** 不得因为 M7～M9 未完成而把项目标记为“未完成”。

投递版本必须能用可复现实例同时证明：

1. 自然语言差旅需求被解析为可检查的会议、政策和行程约束；
2. 公司政策、去程、住宿和市内交通事实可追溯到 Evidence；
3. Orchestrator 按 Task Graph 调度有限 Agent；
4. Gate 能阻断硬错误，Critic 能给出带引用的问题；
5. Repair 只修改受影响范围并重新验证；
6. 报告展示改造前后质量、延迟、成本和失败分布；
7. API、Demo、README、架构图和 CI 使第三方可独立复现。

M7 是高价值进阶项；M8、M9 是岗位定向扩展。当前阶段未完成时，禁止提前开发支付、真实预订、长期画像、缓存或多供应商切换。

## 3. 当前基线

M0～M4 已完成历史验收：已有 Pydantic 契约、状态、Interpreter、Router、Evidence、CandidatePool、Task Graph、Research Agent 和混合规划。历史基线及其适用边界以项目总 Spec 和 `evaluation/` 中的验收证据为准。

M4 验收后发现的当前业务缺口：

```text
商务差旅请求
→ Interpreter 只提取基础字段
→ Router 仍将 PLAN 默认映射为 geo + transport
→ CandidatePool 只有交通候选
→ Composer 只能生成一项交通方案
```

该迁移拆分为三个连续阶段：M4.1 先冻结中国大陆境内单人差旅评测基线，M4.2 修复差旅语义与能力路由，M4.3 接入通用公司政策、去程航班/城际交通、候选级且最多一晚的会前住宿和市内交通，形成 `meeting_arrival_ready` 最小纵向切片。M4 的历史验收不回滚、不改写；M5 必须等待 M4.3 验收。

## 4. 目标技术栈

### 4.1 必选

| 领域 | 技术 | 约束 |
|:---|:---|:---|
| 语言 | Python 3.11+ | 使用现代类型语法；并发研究使用 `asyncio.TaskGroup` |
| 模型 | Pydantic v2 | 跨层 DTO、状态、配置、事件和错误结构 |
| LLM | OpenAI SDK + DeepSeek | 仅通过 `LLMGateway` Port 调用 |
| HTTP | httpx | M3 起用于异步 Adapter，领域层禁止依赖 |
| 政策知识 | PolicyKnowledgePort + 本地 PDF Adapter | M4.3 首版；页码、hash、版本、有效期可追溯 |
| API | FastAPI + Uvicorn | 仅 M6 presentation 层引入 |
| 测试 | pytest、pytest-cov、pytest-asyncio、httpx | 单元/契约/集成/E2E 分层 |
| 日志 | structlog | 结构化、脱敏、带 `trace_id` |
| Trace | OpenTelemetry | Workflow/Task/Agent/Tool/Gate 父子 Span |
| Metrics | prometheus_client | 质量、成功、失败、耗时、调用与修复指标 |
| 存储 | M1 InMemory，M7 最小 SQLite | Repository Port 隔离实现 |

### 4.2 条件引入

- OR-Tools：只有 M4 启发式无法通过基准集且 ADR 证明收益时引入；
- LangGraph：手写 Task Graph 达到可测基线后再评估，不作为前置依赖；
- tenacity、断路器、缓存、备用供应商：仅 M9 允许；
- 向量数据库：不属于 M0～M9 必需范围；本地 PDF 检索基线未证明召回缺口和离线收益前禁止加入；
- 前端框架：M6 默认使用最小静态 HTML/CSS/JS Demo，不为了展示引入独立 Node 构建链。

所有依赖精确 `==` 锁定。新增依赖必须记录用途、替代方案、安全影响和移除成本；禁止因“以后可能使用”预装。

## 7. 全阶段开发协议

### 7.1 固定开发顺序

每个阶段严格执行：

1. **Read**：读取架构、总路线图、当前阶段、AGENTS 和上一阶段报告；
2. **Baseline**：运行前置测试/评测，保存修改前结果；
3. **Contract**：先定义 DTO、Port、错误、状态与失败语义；
4. **Metric first**：先定义组件失败模式、业务北极星、评分方法和阈值，再据此标注 test files 与 evalset；
5. **Component Eval**：使用显式 Fake/Fixture 隔离验证本阶段组件；BLOCKING 组件失败不得被总分抵消；
6. **Stage Integration Eval**：通过公开 Use Case 连接本阶段组件，验证 Schema、关键轨迹、终态和静默部分成功；
7. **Fake first + Live required**：未配置调用必须失败；阶段验收同时通过本阶段规定的真实 LLM/工具验证。Fake 不是运行时降级，也不能单独证明真实模型可用；
8. **Vertical slice**：先完成一个端到端最小切片，再扩同类能力；
9. **Failure injection**：验证超时、非法 Schema、缺失证据、版本冲突和预算耗尽；
10. **Evaluation**：保存 component/integration 分数卡和 baseline/current/diff，再运行本阶段 Live Smoke/Online Eval；解释质量、稳定性、轨迹、成本、延迟和真实 API 偶发失败；
11. **Review**：独立检查分层、状态、证据、安全、可观测性和禁止事项；
12. **Gate**：验收全部通过才更新阶段完成标记；
13. **Handoff**：记录交付、风险、下一阶段前置和 Out of scope。

组件级和阶段集成级评测在 M4.1～M5 随开发持续执行，不等待 M6。M6 只负责将成熟评测组装成包含 P95 延迟、Token/成本、最大步骤、安全和复现性的发布闸门。

### 7.2.1 Offline 与 Live 双轨测试门禁

两类测试职责不同，均不可省略：

- **Offline Suite**：使用显式 Fake、Fixture 和故障注入，验证 Schema、状态、错误传播、超时、非法响应、预算耗尽和无 fallback 行为；默认 pytest/CI 必须零网络；
- **Live Suite**：使用组合根注入的真实 API Key，验证真实供应商连接、模型/Prompt 输出、Schema 通过率、工具响应和端到端质量；标记为 `slow`，并细分为 `live_llm`、`live_tool`、`live_e2e`；
- Live Suite 失败时必须阻断对应阶段，禁止切换 Fake、缓存、估算、备用供应商或部分成功；
- 供应商暂时不可用必须记录为外部依赖失败，阶段不得标记完成；不能把外部失败伪装成代码通过；
- Live 测试必须记录 `model/provider`、Prompt/Schema/rubric 版本、case_id、调用次数、Token、成本、延迟、失败分类和安全摘要，不记录 Key、完整 Prompt 或不必要 PII；
- Live 测试使用固定调用预算、超时和 `retry_count=0`；发现偶发失败后，必须脱敏沉淀为 Fixture，再用 Offline Suite 稳定复现并修复；
- Fake/Fixture 通过不等于真实 API 通过；真实 API 通过也不替代确定性故障注入。

阶段验收的最低形式为：

```text
Stage Pass
  = Offline Suite 通过
  + 本阶段 Live Gate 通过
  + 评测报告和失败分类完整
```

Live Gate 不进入普通无密钥 CI，但必须由本地启动脚本、受保护 CI 或发布前手动命令显式执行。
测试验收采用双轨：Offline Suite 使用显式 Fake、HTTP Stub 和 Fixture 覆盖确定性成功与故障分支；Live Suite 使用真实 LLM/工具 API 做 Smoke 或 Online Eval。Fake 通过不能证明真实 API 可用，真实 API 失败不得切换 Fake、缓存、估算、备用供应商或部分成功。真实失败须脱敏沉淀为 Fixture，加入确定性回归后再重跑 Live Gate。

### 7.2 开工前

- 检查 `git status`，不得覆盖用户已有改动；
- 列出阶段允许修改目录；
- 确认上一阶段验收证据存在；
- 跨阶段依赖缺失时停止并报告，不得顺手补做未来阶段。

### 7.3 实现中

- 一次只实现一个可验证切片；
- 所有时间逻辑依赖 `Clock` Port；
- ID 在边界生成并稳定传递；
- 错误转换为类型化 `WorkflowError` 并保留安全 cause chain；
- 日志先脱敏，只记录必要 ID、状态、计数、版本和时延；
- 状态变更必须记录版本和原因；
- 不做无关重命名、格式化或重构；
- 每阶段新增的现实失败案例必须脱敏后进入回归集。

### 7.4 开发期 strict 模式

M0～M8 默认且强制：

```text
STRICT_MODE=true
retry_count=0
cache_reads=false
fallbacks=false
partial_success=false
```

禁止备用供应商、缓存回退、估算替代、合成成功、占位符补全、Gate 强制通过、循环耗尽视为成功、跳过 Critic/Validator。M9 只能在可关闭 Feature Flag 下逐项改变该行为，strict 模式永远保持上述语义。

### 7.5 Definition of Done

阶段完成必须同时满足：

- 交付物、迁移记录和阶段报告齐全；
- 单元、契约、集成和规定 E2E 通过；
- 失败注入证明异常未被吞掉；
- 覆盖率达到阶段阈值；
- `ruff`、类型检查、`pytest`、阶段 Eval、`git diff --check` 通过；
- 本阶段规定的 Live Gate 通过，且报告中没有未解释的真实 API 失败；
- 无凭证、PII、缓存、运行产物或未脱敏数据进入 Git；
- 文档与代码一致；
- 未实现阶段明确禁止内容；
- 对质量、延迟或成本退化给出阻断或经记录的接受理由。

## 8. 兼容迁移策略

- 保留 `main.py` 稳定入口，内部逐阶段切换到新 Use Case；
- `src/engine/loop.py` 在 M1 由 Facade 包装，不立即删除；
- M2～M5 每迁移一个消费者都增加契约测试；
- 旧模块仅在调用者为零、回归覆盖且本阶段通过后删除；
- 兼容层标记 owner、移除阶段且禁止新增调用；
- 禁止 Big Bang 搬迁后再补测试。

## 9. 阶段交付格式

```text
Stage: Mx
Scope: 本阶段实现范围
Contracts: 新增/修改的类型化契约
Migrations: 兼容层与数据迁移
Tests: 命令与结果
Evaluation: 数据集版本、指标变化、退化案例
Failures verified: 已验证失败场景
Out of scope: 明确未实现内容
Next stage prerequisites: 下一阶段前置条件
```

推荐一阶段一分支、一组可回滚提交。Commit 使用 `AGENTS.md` 的模块标签。
