## 一、M0 在整体路线图中的定位

M0 是总路线图 10 个阶段中的**第 0 阶段**，定位为：

- **不改变用户可见业务能力**的前提下，建立可重复、零网络、fail-fast 的开发基线
- 创建贯穿后续 M1~M9 的版本化评测集
- 解决"当前行为无法可靠回归、架构收益无法量化"的问题

M0 是后续 M1（结构化契约）的前置条件——**M0 未通过时禁止创建 M1 领域契约**。

### M0-W2：严格模式配置（Composition Root）

这是 M0 最核心的架构贡献。共涉及 3 个文件：

#### `src/config.py` — Settings 数据类

```python
@dataclass(frozen=True, slots=True)
class Settings:
    strict_mode: bool = True       # M0~M8 强制 true
    retry_count: int = 0           # strict 下必须为 0
    cache_reads: bool = False      # strict 下禁止
    fallbacks: bool = False        # strict 下禁止
    partial_success: bool = False  # strict 下禁止
    llm_timeout_seconds: float = 30.0
    external_api_timeout_seconds: float = 15.0
    max_revision_rounds: int = 2
    deepseek_api_key: str | None = None
    deepseek_model: str = 'deepseek-chat'
    # ...
```

- **`frozen=True`**：Settings 实例不可变，同一个请求生命周期内共享同一个实例
- **`__post_init__`**：构造时校验 strict 约束——非法组合（如 strict_mode=true 但 retry_count>0）直接抛 `ConfigurationError`
- **`validate_runtime()`**：运行时校验必需 Key 是否存在，缺少 `DEEPSEEK_API_KEY` 时在 Bootstrap 阶段失败，不会进入 LLM 调用
- **`load_settings()`**：从 `Mapping[str, str]`（进程环境或测试显式传入）构造，不主动读 `.env`

#### `src/bootstrap.py` — 组合根

```python
def bootstrap_settings(environ: Mapping[str, str] | None = None) -> Settings:
    settings = load_settings(environ)
    settings.validate_runtime(require_llm=True)
    return settings
```

- 单一入口，确保 `main.py`、测试、Live Smoke 都走同一条创建→校验→注入路径
- 下游组件（`plan()`、`ask_llm()`、`run_l2_review()`）通过参数接收 Settings，不在内部重读环境变量

#### `start-local.ps1` — 本地启动脚本（非 M0 规格，但服务于 M0 理念）

- 白名单机制：只加载 13 个已知变量名到进程环境
- 占位符检测：拒绝 `xxxxxx`、`replace_me`、`<...>` 等占位符
- 进程作用域：`[Environment]::SetEnvironmentVariable($name, $value, 'Process')`，不污染用户/系统环境
- `-ValidateOnly` 开关：只校验配置不启动 Python，不调用外部 API

**这条链路对后续开发的作用**：

1. M1 及之后所有阶段，`Settings` 类可以直接扩展新字段（如 `max_agent_calls`、`evidence_ttl_seconds`），不需要改变创建和注入模式
2. 新组件（Critic、Tool Adapter、Orchestrator）都通过构造函数或方法参数接收同一个 Settings 实例
3. 测试可以注入 `Settings(deepseek_api_key='fake-key')` 而不触发真实网络
4. M3 引入 `httpx` 异步 Adapter 时，超时配置从同一个 Settings 读取
5. M9 的生产韧性（retry/cache/fallback）可以通过 Feature Flag 在 Settings 上扩展，strict 模式永远保持当前语义

### M0-W4：网络隔离、故障注入与观测基线

#### 网络隔离

`tests/support/network.py` 通过 monkey-patch `socket.socket`、`socket.create_connection`、`urllib.request.urlopen` 实现三层拦截。`conftest.py` 的 autouse fixture 确保**所有非 slow 测试零网络**。

#### 故障注入覆盖

验证了以下失败不会转换为正常成功：
- LLM 超时 → `PlanningError(stage='generation')`
- LLM 空响应 → `LLMResponseError` / `PlanningError`
- 工具超时 → `{"error": "..."}`
- 工具空结果 → `{"error": "..."}`
- 修订耗尽 → `PlanningError(stage='revision', retryable=False)`
- 非法 review 形状 → `PlanningError(stage='review')`
- 缺少 API Key → `ConfigurationError`（Bootstrap 阶段，LLM 零调用）

#### 观测基线

- **结构化日志**（`src/obs/log.py`）：structlog JSON 渲染，自动注入 trace_id/span_id，Windows 强制 UTF-8
- **分布式追踪**（`src/obs/trace.py`）：OTel ConsoleSpanExporter，session → agent → llm_call 三级 Span 嵌套
- **Metrics**（`src/obs/metric.py`）：Prometheus Counter/Gauge/Histogram，覆盖 Agent 调用、LLM 调用、Token、重试
- **LLMCallRecord**（`src/gateway/deepseek.py`）：observer 回调模式，不记录 prompt/response/credentials

### M0-W6：基线 Runner 与报告

#### `evaluation/runner.py` — 离线评测 Runner

核心设计：
- **Schema 严格校验**：`load_cases()` 逐字段验证 12 个必填字段，拒绝多余/缺少字段
- **确定性 trace_id**：`uuid.uuid5(NAMESPACE_URL, f'{DATASET_VERSION}:{case.case_id}')`，同一 commit 重跑一致
- **Fake 注入**：通过 `unittest.mock.patch` 替换 `loop.ask_llm` 和 `loop.run_l2_review`
- **双格式输出**：机器可读 JSON + 人类可审阅 Markdown
- **不可采集指标标 `UNAVAILABLE`**：token_usage、api_cost、structured_parse_rate 等当前无法采集的指标明确标记

运行命令：
```bash
venv/Scripts/python evaluation/runner.py --dataset baseline-v1 --offline
```

#### `tests/contract/test_evaluation_runner.py` — Runner 契约测试

验证：
- 数据集包含 32 条 Schema 合规用例
- 离线执行零网络调用
- NOT_SUPPORTED 数量为 25
- Negation recall = 0.5（2 条否定用例中 1 条当前通过）
- L1 budget detection rate = 1.0
- JSON/Markdown 双格式输出正常

## 八、关键学习要点

### 1. Composition Root 是 M0 最重要的架构决策

`src/config.py` + `src/bootstrap.py` 建立的模式将贯穿全项目。它解决了"配置从哪来、谁校验、谁注入"的根本问题——业务模块永远不自己读环境变量，测试可以显式注入 Fake 配置，生产代码从进程环境读取真实密钥。这个模式的价值在 M3（引入多个 Tool Adapter）和 M6（FastAPI 多请求并发）时才会完全显现。

### 2. Characterization Tests ≠ 验证正确性

M0-W3 的特征测试**不验证"输出是否正确"**，而是**锁定当前行为**——当后续阶段重构 `plan()` 时，如果特征测试失败，说明行为发生了改变（可能是预期的改进，也可能是意外的回归）。这种测试策略让你可以安全地重构。

### 3. NOT_SUPPORTED 是诚实的工程实践

32 条评测用例中 25 条标记为 `NOT_SUPPORTED`，每条都标注了"当前为什么做不到"和"目标阶段"。这比写 25 个 `pytest.skip` 或假装通过要诚实得多——新加入的开发者可以直接从数据集了解项目的能力边界。

### 4. Fake 不是降级，是测试工具

`FakeLLM` 未配置响应时会抛 `FakeNotConfiguredError`，不是返回空字符串或默认值。这确保了：如果你写了测试但忘了配置 Fake 响应，测试会立即失败，而不是静默通过。生产代码永远不会使用 Fake。

### 5. 网络 Guard 的 autouse 是安全网

`conftest.py` 的 `network_guard` fixture 是 autouse 的——任何不加 `@pytest.mark.slow` 的测试如果意外触发了网络调用，会立即失败。这防止了"测试写好了但忘了 mock，测试在 CI 里过但在作者机器上依赖外部 API 才能过"的问题。

### 6. Live Smoke 与 Offline Suite 互补

Fake 通过不能证明真实 API 可用，真实 API 通过也不能替代确定性故障注入。两者缺一不可——这是 M0 规格中反复强调的原则，也是双轨测试门禁的核心。
